# A8. Element type is a user-level choice, never hard-coded

The core is generic over the number type `T` so that FP32, FP64, custom types such as DoubleFloats, and ForwardDiff duals all run through the same kernels. Consequences: no float literals in kernels (`zero(T)`, `T(π)`, `eps(T)`); a CI test matrix on the CPU backend over Float32, Float64 and `Dual{Float32,3}`; deposition chooses its accumulation path by a trait on `T` (primitive types use atomics; duals are component-wise linear so per-component atomics are exact, which the tangent-bundle layout uses with one primitive array per tangent, while `Dual`-valued arrays in the test matrix take the sorted path and need no Dual-specific code; compensated types such as Double32/Double64 are not associative component-wise, so they take the sorted segmented-reduction path); a GPU-kernel compatibility spike for DoubleFloats (their `exp`, `sin` implementations inside CUDA kernels are untested here). DoubleFloats is nice to have, not required; if it lacks something the kernels need, drop it rather than work around it. Float32, Float64 and duals are the required set. On consumer cards the candidate for extra precision is Double32 (pairs of Float32 at FP32 throughput, about 48 mantissa bits), not Double64, which inherits the 1/64 FP64 rate. Type genericity also admits instrumentation types (flop counting, error tracking) in tests.
