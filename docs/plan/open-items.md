# ParticleMesh: open items before handoff

Purpose: what the planning side must settle before an implementation team starts from `landscape-and-requirements.md`, `architecture-draft.md` and `sciml-reuse.md`, and what can wait.

## A. Decisions (binding; to change one, edit it here in a PR that says why; git is the history)

A1. **Units and normalization.** The core works in normalized units (c = 1, lengths in c/ω₀ or c/ω_p, fields in m_e c ω/e); the user layer offers SI and possibly other unit systems, as EDM does. ω₀ is the reference frequency (time in 1/ω₀, length in c/ω₀, fields in m_e c ω₀/e, density in units of n_c), matching Smilei; wake quantities in ω_p units are derived views. Nondimensionalize the optimization parameters to O(1), so FP32 tangents are well scaled.

A2. **Baseline numerical scheme, written down as a decision set.** Yee; Boris with half-step momentum centering; Esirkepov current; quadratic shape functions (order 1 only in tests); binomial current filter with a documented pass count; transverse open boundaries (simple absorbing layer first, PML later); laser by antenna plane at the window front; immobile ions; quiet-start loading. The AD-smoothness rule decides ties: prefer the smoother variant. Document each choice with its validation test.

A3. **How parameters enter the simulation.** Density and profile parameters through particle weights, not through particle positions (weights are smooth in the parameters, sampling is not). Laser parameters through the antenna source. Focus position and chirp through the antenna phase. This fixes the tangent seeding and must hold in every injection path, including the moving-window refill.

A4. **Determinism policy.** FP32 atomics make deposition order-dependent (relative run-to-run noise ~1e-7), which breaks finite-difference gradient checks at small steps. Decide: a sort-based deterministic deposition as the reference mode, atomics as the fast mode, bitwise reproducibility as a tested property of the reference mode, counter-based RNG (Philox-style) for particle loading so seeds mean the same thing on every backend.

A5. **Canonical benchmark cases with numbers.** The 1D set (Landau damping, two-stream growth rate, Weibel) with expected values; one 2D LWFA case fully specified (a₀, w₀, τ, n₀, ramp, box, resolution, particles per cell, steps, diagnostics) that is also run in Smilei and PIConGPU (containerized). Experience from earlier cross-code work: matched setups are the under-specified, labor-intensive part; do it once, in a versioned config.
Verification against both PIConGPU and Smilei covers correctness and performance. For the performance comparison to be fair the configs must match shape-function order, current deposition scheme (Esirkepov in all three), filtering, precision (PIConGPU defaults to FP32, Smilei to FP64), particles per cell and output cadence, and run on the same card; report particle-steps per second and cell-steps per second with the GPU model named, never the hostname.

A6. **Repository and environment.** A monorepo; Julia 1.13 (the current release) as the target, CI on 1.13 with the next pre-release as allowed-fail; MIT; public from day one (so no private packages, no hostnames anywhere in the repo, including its `CLAUDE.md`); CI on the KA CPU backend, GPU tests on the local GPU runner. Layout: a Pkg workspace with the umbrella package at the root and `test/`, `docs/`, `benchmark/` and the `lib/` subpackages as members (A11; `lib/` is the pattern EDM uses for `lib/RunManifests`), `scripts/` and `reports/` for results (A13), `docs/plan/` for these documents, `.claude/agents` and `.claude/workflows`, `trace/`, `questions/`.
Relation to EDM: no dependency on ElectronDynamicsModels.jl initially; depend directly on its small public pieces, LaserTypes.jl and GPUDiagnostics.jl (both public GitHub repositories), and lift `RunManifests` out of EDM's `lib/` into its own package or into this monorepo's `lib/`; take the EDM dependency later if enough of it is needed or the symbolic layer earns its place.
Name: **`ParticleMesh.jl`** for the repository and the engine, repository https://github.com/SebastianM-C/ParticleMesh.jl (public); agents work in worktrees inside it through EnterWorktree. Rationale: it names the method family (PIC, PM, P³M, PME) in the SciML style of naming packages after the method (MethodOfLines, NonlinearSolve), it is neutral to the physics so the modules carry the physics names (`Wakefields` for LWFA, a gravity PM module as the near-free generality demo), it is free in General and on GitHub (registry and GitHub availability checked 2026-10-30), and the term already means "differentiable particle–mesh simulation" to the cosmology community through pmwd, which is a positive association rather than a collision; the nearest neighbours are `flatironinstitute/ParticleMeshEwald.jl` (PME via NonuniformFFTs, unregistered) and, outside Julia, pmwd ("particle-mesh with derivatives", the differentiable cosmological PM library) and the Python package pmesh. Rejected: `Wakefields.jl` (too narrow for the umbrella after A9) and `DiffPIC` ("Diff-PIC" is an ICLR 2025 paper, a diffusion-model surrogate for laser-plasma PIC from PNNL and Rochester, so the name would be confusable within the same community). Caveat: mesh-free modules (pairwise interactions, FMM, analytic external fields) are hosted by the engine but not named by it; if those weigh more than expected, `ParticlesAndFields.jl` covers everything at the cost of being vaguer. Subpackage names follow the SciML `lib/` pattern (`ParticleMeshCore`, `ParticleMeshMTK`, `ParticleMeshReactant`, `Wakefields`).

A7. **Acceptance criteria and budgets per work package.** Conservation residuals (Gauss's law to roundoff with Esirkepov, energy drift bound over N steps), agreement thresholds against the benchmark set, a throughput budget (nanoseconds per particle-step on the 4080 SUPER, within a stated factor of Smilei on the same card), memory budget (the `FunctionMap` harness doubles state; on 16 GB that caps 2D with P = 3 at roughly 10⁷ particles), and gradient-check tolerances.
A8. **Element type is a user-level choice, never hard-coded.** The core is generic over the number type `T` so that FP32, FP64, custom types such as DoubleFloats, and ForwardDiff duals all run through the same kernels. Consequences: no float literals in kernels (`zero(T)`, `T(π)`, `eps(T)`); a CI test matrix on the CPU backend over Float32, Float64, Double32 and `Dual{Float32,3}`; deposition chooses its accumulation path by a trait on `T` (primitive types use atomics; duals are component-wise linear so per-component atomics are exact; compensated types such as Double32/Double64 are not associative component-wise, so they take the sorted segmented-reduction path); a GPU-kernel compatibility spike for DoubleFloats (their `exp`, `sin` implementations inside CUDA kernels are untested here). DoubleFloats is nice to have, not required; if it lacks something the kernels need, drop it rather than work around it. Float32, Float64 and duals are the required set. On consumer cards the candidate for extra precision is Double32 (pairs of Float32 at FP32 throughput, about 48 mantissa bits), not Double64, which inherits the 1/64 FP64 rate. Type genericity also admits instrumentation types (flop counting, error tracking) in tests.

A9. **Scope: a generic particle–mesh framework.** Long term the project is a showcase and stress test for Julia and Reactant compiler technology, with modular physics (extensible, possible EDM integration) and connections to packages such as Molly.jl to be explored; all of it long term. Consequences now, none of which change the phase 1–3 schedule: the engine/physics-module split with the electrostatic PIC module as the proof (`architecture-draft.md` §0.1); the Reactant-compatibility rules and a Reactant CPU smoke test in CI from the first package (§0.4); the particle-workload stress-test suite as a deliverable (§0.2); the name (A6). Everything else in §0 is deferred (C). The main integration goal is SciML; Molly compatibility is a nice-to-have, not a design driver. FastMultipole.jl (CUDA for direct interactions only) is not needed for LWFA.

A10. **Problem description separated from numerical implementation.** Principle, the reason to keep the symbolic connection: it enforces a separation of concerns between describing the problem and implementing the numerics. Not blocking; it shapes the kernel interfaces (architecture §0.5, R13). The mesh-solve slot admits Yee kernels and MOL's staggered update now, the MOL Ferrite backend (expected, not public) and Trixi DG later; none of the later ones serves the LWFA module.

A11. **Package environments.** The root `Project.toml` declares a Pkg workspace with `test/`, `docs/`, `benchmark/` and the `lib/` subpackages as members; they resolve together into one root `Manifest.toml`, which is committed, so every worktree and every agent runs the same versions and the depot precompiles them once. `scripts/` is a separate environment outside the workspace, with the root package as a path source and its own committed manifest, so a result is reproducible from the commit alone. Changing a dependency means re-resolving both manifests; CI instantiates both and fails if either changes. The pre-release CI job updates the manifest before testing, since the committed one is resolved for Julia 1.13.

A12. **One role owns dependencies.** Only the `package-manager` role edits a `Project.toml` or a manifest, on a `pkg/` branch; a CI job rejects dependency-file changes on any other branch, so dependency changes are serialized through one branch family and never conflict across worktrees. Work-package records declare the dependencies a package needs, so they are added before the package is dispatched. For an unplanned need, a worker adds the package locally, leaves the dependency files out of its PR, and posts a request on the pinned issue "Package requests"; the role answers with a PR. The same role runs the weekly update (`Pkg.update()`, tests, benchmark suite, compat investigation, compat caps explained in the PR) and routes real upstream bugs through the `upstream-reporter` role.

A13. **Results, plots and reports.** `scripts/` holds the user code that produces results: benchmark cases with expected values, validation and cross-code comparison runs, campaigns, and the figures reports embed; outputs go to `scripts/runs/` (ignored) and every run is recorded in `trace/` with its inputs hashed. All plots are made with CairoMakie from `scripts/`, never from package code (Makie recipes may live in a package extension); each plot is a PNG next to a JSON sidecar with the scalar values it shows, so agents and the trace builder read numbers, not pixels. Reports are Markdown in `reports/`, one directory per report with the figures committed, headed by the work package, the commit, the run ids and the input hashes, so a report is a record. The current-state view is a static page the trace builder generates from `trace/graph.json`, the latest digest and the report index, published by CI to GitHub Pages on every merge to `main`; the overseer may publish the same page as a Claude artifact for a private, commentable copy (to verify: Artifact tool availability in the overseer's session type, and that artifact comments reach it).

A14. **Merge policy.** `main` is protected by a ruleset: pull requests only, squash merges, one approving review, review from the code owners for the tier-2 paths in `.github/CODEOWNERS`, required status checks (the CI jobs and the review gate), no bypass for agents (repository admins may bypass on pull requests only; cloud sessions act as the owner's account and so hold that bypass technically, and only the contract keeps them from merging). Tier 0 and tier 1 PRs merge unattended: `.github/workflows/review.yml` runs two reviewer lenses (numerics, code; briefs in `.claude/agents/`, read from the base branch) on every non-draft PR and its gate job approves or requests changes as `github-actions[bot]`; the PR author enables auto-merge after opening the PR, and GitHub merges and deletes the branch when the requirements are met. Tier 2 PRs wait for the owner's approval in addition; the owner can approve from any device. Two repository settings are prerequisites: "Allow GitHub Actions to create and approve pull requests" (the gate's approval) and the ruleset's dismissal of stale approvals on push (so a new commit is reviewed again before it can merge). Identities: local factory sessions act on GitHub as the GitHub App `particlemesh-factory[bot]` (one-hour installation tokens, the app installed on this repository only, no Workflows permission so agents cannot change CI), which keeps the owner's reviews and comments distinguishable from agents'; cloud sessions act as the owner's account through Anthropic's GitHub proxy, which also rejects GraphQL, so they do not run `gh pr` or `gh issue`. The `package-manager` role also runs as a workflow (`.github/workflows/package-manager.yml`, on comments to "Package requests", weekly, or by hand) with the app's identity; Dependabot keeps the Actions versions current and the package-manager approves its PRs. The overseer's digest reports what merged, and a revert is one PR.

## B. Thin spots in the plan (fill in during planning or as the first spike of a phase)

B1. **Moving window mechanics.** Specify: advance by whole cells every k steps; fields shifted by an index offset (circular buffer) rather than memory moves; particle positions in window coordinates with a global offset; refill at the front sampling the global density profile; drop at the back. With slab decomposition this becomes a ring rotation of ranks; write that down before anyone implements the single-device version so the data layout already fits.

B2. **Envelope model is a sub-project, not a free cost reduction.** It needs an envelope equation solver (second order in time, with the Smilei/INF&RNO-style scheme), a modified pusher with the ponderomotive force and the |a|²-corrected γ, and a susceptibility deposition. Scope it as its own phase with its own validation (envelope versus full PIC in 2D).

B3. **Differentiable diagnostics.** Histograms and "cut-off energy = max" are not differentiable. The diagnostics module should offer soft binning or kernel density estimates, smooth maxima (log-sum-exp with a temperature) and quantiles. This is independent of the objective decision but should exist before it.

B4. **Reduced-model equations and references.** Level 0 (1D nonlinear quasi-static wake, test electron with dephasing) is covered by the Esarey–Schroeder–Leemans 2009 review; the bubble-regime scalings usually attributed to Lu et al. 2007 are not yet verified as a citation. The r-z quasi-static fluid model of level 1 has no pinned reference yet; verify one before writing the spec.

B5. **FP32 validity.** JAX-in-Cell reports deviations in 32-bit; the cell-plus-offset layout fixes positions but momenta and fields still drift. Plan an FP32-versus-FP64 drift test on a rented FP64-capable GPU as part of phase 2 validation and decide which quantities (energy sums, deposition accumulators) stay FP64.

B6. **Symbolic spike acceptance.** The claim that an MTK-generated force runs inside a KA kernel with duals needs a pass/fail test: generated function inlined into a GPU kernel, correct on CPU and GPU, `Dual` inputs accepted. DiffEqGPU does this already, so the risk is low, but the team should not discover the details mid-phase.

B8. **Machine availability.** Hardware: one local RTX 4080 SUPER and rented GPU VMs. GPU runs are launched on demand through the `gpu-runner` session that factory sessions message (see `CLAUDE.md`); unattended GPU work is deferred, with rented GPU VMs as the later option. Cloud means Anthropic-hosted agent sessions (CPU only, no Julia preinstalled) for CPU-side work, and rented GPU VMs when a second or larger GPU is needed; EDM's campaign backends (`orchestration/backends/` in ElectronDynamicsModels.jl: local, Hot Aisle, RunPod, Verda) can be borrowed for those. Plan phases 1 to 3 around one local GPU; treat anything larger as rented.

B9. **Reactant compatibility spike** (before the first GPU package). Compile one electrostatic step (KA kernels through `ReactantBackend`) with `@compile` on CPU; check raising (`raise=true`) of gather, both deposition variants, sort and compaction, and the Yee stencils; measure compile time; run `Enzyme.gradient` on the raised step with `raise_first=true`; find out whether `Dual`-valued locals inside a raised kernel survive (if not, forward mode on the Reactant path is Enzyme-MLIR forward, rule 8 of §0.4); check scatter-add determinism on the GPU. Outcomes become run records; failures become upstream issues with minimal reproducers. Include the harness: one `SimpleFunctionMap` solve around the step under `@compile`, reusing the existing SimpleDiffEq-on-Reactant work, and a note on OrdinaryDiffEq PR #4436's status, including whether it covers `FunctionMap` in `OrdinaryDiffEqFunctionMap` (unverified).

B10. **Molly interface study.** Half a day reading Molly's `System`, interaction and simulator types and `src/interactions/ewald.jl` (PME with KA kernels) to settle the names and signatures of the container and interaction interfaces (§0.1) before the engine skeleton freezes them; no code dependency on Molly.

B7. **Multi-GPU prerequisites.** Check CUDA-aware MPI and the device interconnect topology on the rented multi-GPU instance before the 3D phase; decide device-to-device copies versus MPI for the single-node case.

B11. **Unverified platform fact.** Whether workflow agents fire Claude Code hooks is not confirmed (`factory-and-observability.md` §3); check it before relying on hook-written session records for workflow runs.

## C. Can wait (phase 4 and later)

Reactant as a production backend (2D on Reactant-CUDA, sharding, multi-host, TPU), reverse mode and checkpointing, 3D block decomposition and load balancing, PSATD or Lehe solver, ionization injection, quantum-corrected radiation reaction, MOL staggered backend beyond the spike, P³M and Molly interoperability (AtomsCalculators/AtomsBase), EDM symbolic forces inside raised kernels, FEM (MOL Ferrite backend) and DG (Trixi) Maxwell backends, PointNeighbors for the pairwise slot.

## D. Dependencies and risks to keep visible

- Checkpointing.jl: not a dependency (maintenance status unknown). Reverse mode over the PIC loop will use in-house checkpointing: periodic two-level checkpoints of the full state over the fixed-step loop with Enzyme per step is a few dozen lines; the binomial (Revolve) schedule is a published algorithm and can be implemented in-house with tests if memory forces it; Reactant's traced loops with checkpointing remain the alternative on that path.
- Reactant and Enzyme-on-CUDA move fast with open correctness bugs (Oct 2026); nothing in phases 1 to 3 may depend on them.
- MethodOfLines stays a dev dependency of the optional extension only, never of the core.
- Reactant raising covers a growing but incomplete class of kernels and the compile time of a many-kernel step is unmeasured; the CI smoke test and B9 keep this visible without letting phases 1 to 3 depend on it.
- OrdinaryDiffEq's Reactant path is a draft PR (#4436); the Reactant time loop uses SimpleDiffEq or a `@trace` loop until it lands. The MOL Ferrite backend has no public trace yet; do not plan around it.
- The `FunctionMap` harness's double buffering and the tangent layout both multiply memory; a 2D case must be sized for the 4080 explicitly.
- The objective and the gradient-versus-Bayesian decision must land before the tangent layer is frozen (end of phase 2), because they fix which parameters are active and which diagnostic is reduced.

## F. Process: agent teams, loops and observability

Premise: the project is also an experiment in software-factory approaches, with a significant part of the implementation done by autonomous agent teams and loops, and a required observability layer that traces how cascading requirements propagate. Design and platform facts in `factory-and-observability.md`. The traceability layer (content-addressed requirement, decision, interface, work-package, test, run and session records with staleness propagation) should exist in a minimal form before the first work package starts, so that every session is recorded from day one.

## G. First batch: CPU-only packages as cloud sessions

Plan in `factory-and-observability.md` section 3c: local prerequisites (public repo, `CLAUDE.md`, role definitions, cloud environment with the Julia allowlist and a cached setup script), then four or five parallel cloud sessions or Project threads on the CPU-only packages (trace MVP, core skeleton, 1D3V benchmarks with plots, level-0 reduced model, plan review). Decisions A1 to A13 and the benchmark numbers of A5 must be in the repository before the sessions start, or they will guess.

## E. What the implementation team should receive

A work-package list with, per package: scope, the interface it implements, the acceptance tests and budgets from A7, what it must not do, and the decision log entries it depends on. The planning documents are the input; the work-package spec is the next planning deliverable.
