# ParticleMesh as a software-factory experiment: agents, loops, observability

Companion to `open-items.md`. Status: draft; the agent-platform facts are from the Claude API reference bundled with Claude Code (2026-10) and the Claude Code docs as cited; verify prices and limits against the current platform documentation before relying on them.

Premise (A0): a significant part of the implementation is done by autonomous agent teams and loops; the owner sets the goals and monitors; the process itself is an experiment. Two things are therefore first-class deliverables next to the code: links that show how the goals propagate into work, tests and runs, and an observability layer over the agents that do the work.

## 1. Traceability: links in the files, history in git

The owner's aims and decisions are files under `docs/goals/` (A0 to A10). Everything below them is derived by the factory: requirements and interfaces as prose in `docs/plan/`, work packages in `trace/wp/`, tests in the code. Git already holds the history, the diffs and content addresses; the trace layer adds only the links between those files and one check over them. The specification is `trace/README.md`.

- **Links, staleness, cascade and checker**: `trace/README.md` (front matter and test tags, staleness by git blob id, the re-derive run after a goal edit, `scripts/trace/build.jl`).
- **Runs and sessions.** A run hashes the inputs it reads that live outside git (F3). Agent sessions are measured by telemetry and hooks (section 3), not by records written by hand.

## 2. Compute topology for the agents

The hard constraint is where the hardware is. Cloud-hosted agents can do CPU-backend development, tests, documentation, trace maintenance and reviews. Anything with CUDA, the Smilei and PIConGPU comparisons, and campaigns needs the local 4080 SUPER or a rented GPU VM. Two ways to connect hosted agents to that hardware exist (section 3); the fallback is Claude Code sessions running on the machine itself.

Suggested split:
- Cloud, autonomous: core numerics on the KA CPU backend, unit and conservation tests, documentation, requirement-graph maintenance, first-pass reviews, nightly trace rebuilds.
- GPU machines, autonomous but budgeted: CUDA backend work, kernel benchmarks, FP32-versus-FP64 drift tests, cross-code validation, campaigns.
- Human: the goals and decisions in `docs/goals/`, the factory settings (section 5), vetoes from the digest, final review of gradient claims.

## 3. Platform facts (verified from the bundled Claude API reference, 2026-10)

### Managed Agents (Claude API, beta)
- Agent configs are persisted and versioned; sessions pin to a version. Sessions stream events; a Console session viewer shows transcript, per-tool statistics, tokens in and out and cost per session with no setup.
- **Self-hosted sandboxes**: `config: {type: "self_hosted"}` keeps the agent loop on Anthropic's side while bash, file operations and code run in a container you control through an outbound-polling worker (`EnvironmentWorker.run()` in the SDK or `ant beta:worker poll`). This is the route to GPU hardware: the worker runs on the GPU machine and only needs outbound connectivity. Verified details: the worker is `EnvironmentWorker` in the Python, TypeScript or Go SDK (always-on `run()`, or `handle_item()` for one claimed work item), or `ant beta:worker poll` with the fixed built-in toolset (bash, read, write, edit, glob, grep); a per-session container is spawned from the poller's `--on-work` script (the reference shows `docker run` with the forwarded `ANTHROPIC_*` variables); a webhook on `session.status_run_started` can wake the poller instead of keeping it always on; the host needs `/bin/bash` and a POSIX filesystem. The reference does not mention GPUs at all: GPU access is a property of the container you spawn (GPU passthrough in the run script), not something the platform provides or blocks. Sessions in a self-hosted environment cannot attach file or GitHub-repository resources (cloud environments only); the repository must be present in the container.
- **Session budgets**: a hard cap in list cost set at session creation; the session pauses at the cap and resumes only when the budget is changed or removed. List cost counts model tokens at list price, web searches, and running time at $0.08 per hour.
- **Outcomes**: a session can be started with a rubric; a separate grader iterates the agent against it until it passes or hits a maximum number of iterations. Work-package acceptance criteria map directly onto such rubrics.
- **Scheduled deployments**: cron-scheduled sessions with per-run records and budgets, for nightly validation or trace rebuilds.
- **Multi-agent sessions**: a coordinator with a roster of subagents sharing one container, plus dynamic workflow runs for fan-out work.
- **Observability**: `session.usage` events with cumulative tokens and list cost; `span.model_request_end` events with per-request token usage; webhooks on state transitions; OpenTelemetry export both from the SDK (client side) and from the API (server side, configured by an org admin through the Admin API or Console) into any OTLP backend. The API-side spans cover each model request and each Managed Agents turn; SDK-side spans cover client tools and tools in a self-hosted sandbox.
- Billing: sessions are priced at API rates plus runtime (the reference only states list-price mechanics).

### Claude Code side (from code.claude.com docs, 2026-10-30)

- **Agent teams** (experimental, `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`): a lead plus teammates, each a full session with its own context, sharing a task list and mailbox; spawned only from interactive sessions, never from `claude -p` or the Agent SDK; one team per session, no nesting, all teammates on the lead's machine (team state under `~/.claude/teams/`); hooks `TeammateIdle`, `TaskCreated`, `TaskCompleted`. Docs: https://code.claude.com/docs/en/agent-teams.md
- **Workflows** (`Workflow` tool, `/workflows`): JavaScript scripts orchestrating subagents in the background with `agent()`, `pipeline()`, `parallel()`, `phase()`; resumable with cached agent results; saved to `.claude/workflows/` and run as `/<name>` with `args`; 16 concurrent agents by default, 1,000 per run; counts against subscription usage with no per-run dollar cap; the `ultracode` keyword is ignored from `-p` and scheduled tasks, but a saved workflow can run unattended from `claude -p` when `Workflow(<name>)` is allowed and the subagents' tools have allow rules; subagents cannot launch workflows. Docs: https://code.claude.com/docs/en/workflows.md
- **Scheduled tasks** (`/schedule`, research preview): run on an Anthropic cloud VM (4 vCPU, 16 GB RAM, 30 GB disk, no GPU, no Julia preinstalled) or, for Team and Enterprise plans only, a self-hosted environment; triggers are cron (hourly at most), an API fire endpoint, and GitHub events; results are cloud sessions with transcript, diff and PR; counts against subscription usage. Local alternative: Desktop scheduled tasks on your own machine. Docs: https://code.claude.com/docs/en/routines.md
- **Remote Control**: the local `claude` process does the work on your machine (so on the GPU boxes), reachable from web and mobile through outbound HTTPS polling only; `claude remote-control` server mode keeps many sessions (`--capacity`, `--spawn worktree`); needs a claude.ai login, not an API key or setup token, which matters for headless boxes (log in once interactively, keep it in tmux); server mode gives up after about ten minutes of network outage. Cross-session messaging reaches sessions on other machines through it. Docs: https://code.claude.com/docs/en/remote-control.md , https://code.claude.com/docs/en/cross-session-messaging.md
- **Cloud sessions** (`claude --cloud`): Anthropic VM, cannot drive local machines; `--teleport` pulls a session back. Docs: https://code.claude.com/docs/en/claude-code-on-the-web.md
- **Telemetry**: `CLAUDE_CODE_ENABLE_TELEMETRY=1` with OTLP metrics and logs exporters (set in the shell or `~/.claude/settings.json`, not project settings); metrics for sessions, cost (estimate), tokens by type, tool decisions, active time, with attributes `agent.name`, `skill.name`, `model`, `effort`, `query_source`; per-tool events `tool_decision` and `tool_result` with duration and error type; beta traces (`CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1`) with spans for interactions, LLM requests and tools, and `agent_id`, `parent_agent_id`, `workflow.run_id` identifiers; prompts and tool parameters redacted unless opted in. Docs: https://code.claude.com/docs/en/monitoring-usage.md
- **Hooks**: 33 events including `SessionStart`, `SessionEnd`, `PreToolUse`, `PostToolUse`, `Stop`, `SubagentStart`, `SubagentStop` (with the last assistant message), `TaskCompleted`, `TeammateIdle`; handler types `command`, `http` (POST JSON), `mcp_tool`, `prompt`, `agent`; inputs carry `session_id`, `transcript_path`, `agent_id` (whether workflow agents fire hooks: open-items B11). Subagent transcripts live under `~/.claude/projects/<project>/<session>/subagents/` with a 30-day default cleanup. Docs: https://code.claude.com/docs/en/hooks.md
- **Reproducible roles**: `.claude/agents/*.md` frontmatter pins `model`, `effort`, `tools` allowlist, `disallowedTools`, `permissionMode`, `maxTurns`, `skills`, `hooks`, `isolation: worktree`; a teammate spawned from such a definition takes its tools, model and effort; `CLAUDE_CODE_EFFORT_LEVEL` overrides everything; 20 concurrent subagents and depth 3 by default. Docs: https://code.claude.com/docs/en/sub-agents.md
- **Managed Agents cloud sandbox** (for comparison): Ubuntu 24.04, up to 8 GB RAM and 10 GB disk, no GPU, Julia not preinstalled; self-hosted sandboxes accept only memory-store resources, so the repository must already be in the container. Billing is API billing, as the session budgets above count it; whether self-hosted sandboxes incur the runtime charge is not stated. Docs: https://platform.claude.com/docs/en/managed-agents/cloud-sandboxes-reference.md , https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes.md , https://platform.claude.com/docs/en/about-claude/pricing.md

Two constraints follow for the factory. No hosted surface has a GPU or Julia; every GPU task and, in practice, every task that must compile the Julia stack runs on machines we control, reached through Remote Control (subscription) or a Managed Agents self-hosted worker (API billing). And the "autonomous team" primitives differ in how unattended they can be: agent teams need an interactive lead; saved workflows run unattended from `claude -p` with allow rules; Managed Agents sessions and deployments are unattended by construction and are the only ones with hard dollar caps.

## 3b. Visualization as the inspection channel

Design premise: much of the inspection is plot-driven. Three audiences read them: the human reviewer, the agents doing the work (Claude reads images, so a plot is an input an agent can act on), and the dashboard. Consequences for the design:

- **A standard plot set per run, generated from the run record, not ad hoc.** Fixed names, fixed layouts, fixed axes conventions, so that two runs or two codes are comparable at a glance and an agent can ask for "the standard set" and read it. Physics set: field slices (E_z, E_y or laser envelope, density), longitudinal lineouts of the wake, phase space (x, p_x) of plasma and bunch, energy spectrum and cut-off, conservation residuals versus time (energy, Gauss's law), and for AD runs the tangent fields and the gradient-versus-finite-difference plot. Cross-code set: the same panels overlaid for ParticleMesh, Smilei and PIConGPU on the matched case. Performance set: particle-steps per second versus particle count and GPU, roofline-style points.
- **Numbers next to every plot.** Agents reason better with a figure plus the few numbers it encodes (peak field, cut-off energy, residual norms), so each standard plot is emitted together with a JSON sidecar of the plotted scalars (F3), and the digest and the reviewers read the sidecar, not the image.
- **Plots are derived records.** The EDM pattern applies directly: a plot is a `derived` sidecar that depends on a run id, with the script, commit and parameters recorded, so a plot can always be regenerated and the dashboard can group them into sweeps. Plots are made from `scripts/` (F3); Makie recipes on the solution and diagnostic types may live in a package extension, so the same call works for a CPU test and a GPU campaign.
- **Factory views are plots too.** The goal coverage (goals, packages and tests, stale packages highlighted), test status over commits, and cost and tokens per work package over time belong in the same dashboard, so that "what changed and what does it affect" is answered by looking rather than by reading files.
- **Agent review loops can be plot-driven.** A work package's rubric can require specific standard plots and state what they must show (for example: the two-stream growth-rate fit overlays the analytic slope; the Gauss residual stays flat at roundoff). The grader or reviewer agent reads the plot and the sidecar numbers; the human sees the same artifacts in the dashboard.


## 3c. Billing surfaces and where each kind of work runs

Verified billing facts (code.claude.com, platform.claude.com, 2026-10-30):
- Cloud sessions, cloud scheduled tasks, Projects threads and ultrareview run on Anthropic VMs and "count toward your plan's usage limits ... there's no separate charge for the cloud VM".
- The Agent SDK (Claude Code as a Python or TypeScript library, same tools, hooks, subagents, sessions and `.claude/` loading) must use API-key authentication; claude.ai login is not allowed for SDK agents. Managed Agents is API billing too.
- Cloud VM: the one scheduled tasks run on (§3), with Docker available. Julia is not preinstalled and `julialang.org` is not on the Trusted allowlist (`*.amazonaws.com` and GitHub release assets are, so juliaup binaries pass but `pkg.julialang.org` does not). A Custom network list with `julialang.org`, `*.julialang.org` and `pkg.julialang.org` fixes that. A setup script runs once per environment and its filesystem snapshot is cached only if it finishes in roughly five minutes, for about seven days; Docker images it pulls are kept in the cache.
- Projects (public beta, gradual rollout): one coordinating conversation starts a thread per task, each a cloud session on its own branch with a pull request and auto-fix, sharing project instructions and memory; threads get each repository's `CLAUDE.md` but not its skills, settings or MCP config; thread model and effort are project settings (default Opus at high effort); a thread can run on your own computer through Remote Control when it needs local hardware.

### Cloud sessions: prerequisites

The first implementation runs as small sequential spikes (A0), not as a parallel batch of cloud sessions. A cloud session that takes a CPU-only package needs: the public repository with the planning documents under `docs/plan/`, a `CLAUDE.md` with the conventions, `.claude/agents/` role definitions, and a cloud environment with the Custom network list and a setup script that installs juliaup plus Julia 1.13 and instantiates the core package's dependencies inside the five-minute cache window (KernelAbstractions and a handful of deps fit; the SciML stack for the reduced models does not, so either precompile it in a SessionStart hook per session or pull a prebuilt depot image with Docker in the setup script). Install the Claude GitHub App on the repository. Rate limits are shared across all sessions, so parallelism costs proportionally.

### API-billed work: the GPU side

- An Agent SDK script on the 4080 box under an API key, run on demand: validation and benchmark campaigns, FP32-versus-FP64 drift tests, cross-code comparisons against Smilei and PIConGPU, using the repository's role definitions and reporting through telemetry and hooks. This is the API-billed autonomous GPU loop; a truly unattended version waits for rented GPU VMs.
- Managed Agents with a self-hosted worker on the same box for a few well-specified GPU work packages, to try budget-capped, rubric-graded sessions.
- Cheap plumbing: Batch API grading of plot sets and sidecars at half price, API-side OpenTelemetry tracing.

API-billed sessions are sized for nightly loops, not for bulk implementation.

## 3d. The overseer: one Claude with the overall view (no GPU needed)

Projects is in gradual rollout (2026-10-30), so the coordinating view is built independently of it. Its job is to read, compare and report, never to compute:

- Inputs, all in the repository or published by it: the goals, the planning documents and the work packages with the checker's output, open branches and pull requests with their CI results and test reports, the standard plots with their scalar sidecars, run records from GPU campaigns, agent cost and usage from telemetry. GPU work produces artifacts that get committed or published (the EDM pattern: run manifests, plots, dashboard); the overseer reads artifacts, so it needs no GPU. If it concludes something must be re-run, it files a task for the GPU loop instead of running it.
- Checks: stale work packages after a goal edit; each branch or PR against its work package (interface implemented, tests tagged with goal or package ids, plot set present, budgets met); drift between goals and code (normalized units, no float literals, no hostnames, generic element type) via scripts; progress and cost per work package from telemetry; goal-level questions that need a human.
- Outputs: a dated report in the repository (and the dashboard), issues for concrete gaps, and a list of proposed next sessions as ready-to-paste `claude --cloud "..."` commands, which is the part of Projects worth replacing by hand.
- Tooling constraint: the checker is a short Julia script in `scripts/`; a session without Julia reads the work-package front matter directly, which is plain TOML.

Hosting: the overseer runs from a local launcher on a timer, in auto mode, in its own worktree; it needs no GPU. The later option, with the same prompt and tools, is a **Managed Agents scheduled deployment**: a versioned agent with a GitHub repository resource and a vault credential for pushing, a memory store for what it flagged before, a hard budget per run, webhooks for notifications, Console cost per session. API-billed. The Managed Agents cloud sandbox (§3) is enough for reading and running Python checks. Migrate the role once the GPU loop exists.

## 3e. Human interface: steering without becoming the bottleneck

Premise: the human reviewer cannot read every line, and frequent approval requests cause approval fatigue. Design goals: review artifacts rather than code, replace approvals with gates and budgets, batch the decisions that remain, and loosen gates as the track record justifies.

**Three levels of human attention**
- Goals and decisions (rare, highest leverage): editing `docs/goals/` is the steering wheel; the planner re-derives what depends on the edit and the digest lists what it changed.
- Acceptance evidence per work package: the standard plots with sidecars, conservation residuals, benchmark agreement, gradient checks, the two agent reviews and the overseer's verdict, all on one page. The human reads evidence, not diffs.
- Diffs: only for the goals, the factory's own configuration, and anything that supports a scientific claim leaving the machine (independent review before a claim leaves the repository; see `CLAUDE.md`). Interface changes are derived work: they merge on the automated review and the digest flags each one.

**Risk tiers decide what needs a human, assigned from file ownership (F4)**
- Tier 0 (docs, tests, plots, work packages, benchmark data) and tier 1 (implementation, interfaces and derived requirements in `docs/plan/`): merge unattended once the required checks and the automated review pass.
- Tier 2: the paths `.github/CODEOWNERS` lists, which wait for the owner as F4 says. Everything derived from the goals is tier 0 or 1: the owner vetoes it from the digest instead of approving it.
- Merge policy, review gate and enforcement: F4.

**No blocking questions.** Agents never stop to ask; the rule is in `CLAUDE.md` ("Working here"). Workflow agents cannot ask anyway. The overseer folds open questions into the digest; answering one is editing the file or a one-line reply, or an edit of a goal when the answer changes one.

**Permissions.** What sessions do under auto mode and under exact allow lists is in `CLAUDE.md` ("Working here"). The auto-mode classifier is configured in the factory's own settings outside the repository, because the classifier ignores project settings, with every shell command classified rather than passed by an allow rule. In a non-interactive run a denied action is skipped and the session goes on, so each denial is logged on the machine and the overseer reports them in the digest. The GPU runner keeps narrow allow rules: its command surface is fixed, and it holds the GPU.

**Issues in this repository, never elsewhere.** What agents may file and how they label it is in `CLAUDE.md` ("Issues"). Humans and sessions outside the factory triage: file upstream, change the rule, role or machine setup, and close the issue. The digest lists open issues by label.

**Surfaces, in order of frequency**
- A daily digest from the overseer, 15 to 20 minutes to read: what landed, what is waiting (tier-2 items and open questions, each with a default), what the nightly GPU loop found, cost and progress per work package, proposed next sessions as ready-to-paste commands. Delivered to the dashboard and, optionally, exported as a PDF for annotation.
- The dashboard: goal coverage with the stale packages, work-package status, the plot sets, review precision and defect statistics.
- One steering session: a local Claude Code session (reachable remotely through Remote Control) where directions are given in natural language and turned into edits of the goals, questions answered, sessions launched.
- PR comments for the rare line-level remark; tier-2 approvals from the phone as they come; a weekly hour for the goals.

**Trust calibration.** The dashboard tracks agent-review precision (findings confirmed versus refuted), defects found after merge by CI or the nightly loop, and reverted PRs, per tier. Tiers loosen on evidence (a package type moves from tier 1 to tier 0 after N clean merges) and tighten on a defect. Start strict.

**Brakes.** One switch pauses everything: scheduled tasks paused, workflows stopped, Managed Agents budgets set to the consumed amount. Budgets per session and per work package cap the damage of a runaway loop without anyone watching.

## 4. Proposed factory shape (to discuss)

1. The owner's goals in `docs/goals/` are the root; requirements, interfaces and work packages are derived from them and link back by goal id.
2. Each work package runs as one budgeted session: cloud environment for CPU-only packages, self-hosted sandbox on a GPU machine for the rest, started with the package's rubric as the outcome. Its cost comes from telemetry.
3. A scheduled job runs the checker and the CPU test suite and starts a planner run for stale packages.
4. Human gates: goal edits, the factory's configuration, and anything that makes a scientific claim. Merges of derived work are automatic; the owner vetoes from the digest.
5. Cost and progress per work package come from telemetry, next to the coverage the checker prints.

### The split (`overview.md` §3)

- **Bulk implementation: Claude Code saved workflows run on the GPU machine.** One workflow per work-package type (implement → test → plot-inspect → review → report), stored in `.claude/workflows/`, started either from an interactive lead session or unattended with `claude -p "/<workflow> WP-xx"` under explicit allow rules, on the local 4080 SUPER box with a warm Julia depot and the GPU (rented GPU VMs are the scale-up). A primer and a first read-only workflow are in `workflows-primer.md`. This spends subscription usage, keeps Julia compile times out of cloud sandboxes, and gives the trace layer `workflow.run_id` and `agent_id` for free through telemetry.
- **Roles as subagent definitions** in `.claude/agents/`, with model, effort and tool lists in their frontmatter and per-run overrides in the workflows that start them: implementer, numerics reviewer, code reviewer, plot inspector, overseer, and three service roles, `upstream-reporter` (minimal examples for `upstream` issues), `package-manager` (the weekly dependency update and Dependabot, F2) and `janitor` (the mechanical items of the `follow-up` issues the review gate files; anything needing a decision stays in the issue for the planner).
- **Loops**: desktop scheduled tasks or the Agent SDK script on the 4080 for validation and benchmark campaigns; the overseer from a local launcher on a timer (§3d); Claude Code scheduled tasks in the cloud for CPU-light chores such as trace rebuilds and documentation checks.
- **Managed Agents as a bounded second track**, not the backbone: rubric-graded outcomes and hard session budgets for a few well-specified work packages, and cron deployments with a self-hosted worker on a rented GPU VM for unattended GPU validation. It is the only surface with dollar caps and per-session cost records, so it is also the cheapest way to measure what a work package costs. Prerequisites: a worker container with Julia, the depot and GPU passthrough.
- **Observability pipeline**: OpenTelemetry metrics, logs and beta traces from Claude Code and, if used, API tracing from Managed Agents, into one OTLP backend; hooks (`SubagentStop`, `TaskCompleted`, `SessionEnd`) can add the work-package id to the telemetry so cost is attributed per package; the dashboard reads the checker's coverage output plus the standard plots.
- **Human gates** unchanged: goal edits, the factory's configuration, scientific claims.

Open questions: whether to keep the Managed Agents track at all for a single-maintainer project (cost and plumbing versus the budget and outcome features), the OTLP backend (a self-hosted Grafana stack versus a hosted one).


## 5. Factory settings (F1 to F4)

How the factory runs, as it stands; owned by the owner like the goals (tier 2), but outside the goal links. They were decisions A11 to A14 before the goals moved to `docs/goals/`.

F1. **Package environments.** The root `Project.toml` declares a Pkg workspace with `test/`, `docs/`, `benchmark/` and the `lib/` subpackages as members; they resolve together into one root `Manifest.toml`, which is committed, so every worktree and every agent runs the same versions and the depot precompiles them once. `scripts/` is a separate environment outside the workspace, with the root package as a path source and its own committed manifest, so a result is reproducible from the commit alone. Changing a dependency means re-resolving both manifests; CI instantiates both and fails if either changes. The pre-release CI job updates the manifest before testing, since the committed one is resolved for Julia 1.13.

F2. **Dependencies.** Any pull request may add or change a dependency: the session runs `Pkg.add` in its own worktree, adds a compat entry for every direct dependency of the root and `lib/` packages, and lists the change in the PR description. Work packages name the dependencies they need, so the planner orders packages that add them rather than running them at the same time. A `Manifest.toml` conflict after a rebase is resolved mechanically; the procedure, and the courtesy note to other sessions on the machine, are in `CLAUDE.md`. `scripts/Manifest.toml` is re-resolved whenever the root manifest changes, and CI checks that both instantiate without changing. The engine's `Project.toml` files (root and `lib/`) are code-owner paths, and the trace check rejects the packages the engine must not depend on (ModelingToolkit, MethodOfLines, Molly, Checkpointing; `trace/README.md`). The `package-manager` role runs the weekly update (`Pkg.update()`, tests, benchmark suite, compat investigation, compat caps explained in the PR description) and checks the Dependabot pull requests; it does not own the dependency files. Real upstream bugs go to the `upstream-reporter` role.

F3. **Results, plots and reports.** `scripts/` holds the user code that produces results: benchmark cases with expected values, validation and cross-code comparison runs, campaigns, and the figures reports embed; outputs go to `scripts/runs/` (ignored), each run writes a manifest next to its outputs (commit, inputs with their hashes, hardware), and a report commits the manifests of the runs it cites. All plots are made with CairoMakie from `scripts/`, never from package code (Makie recipes may live in a package extension); each plot is a PNG next to a JSON sidecar with the scalar values it shows, so agents and the digest read numbers, not pixels. Reports are Markdown in `reports/`, one directory per report with the figures committed, headed by the work package, the commit, the run ids and the input hashes, so a report is a record. The current-state view is a static page generated from the trace checker's coverage output, the latest digest and the report index, to be published by CI to GitHub Pages on every merge to `main` (planned; no workflow does it yet); the overseer may publish the same page as a Claude artifact for a private, commentable copy (to verify: Artifact tool availability in the overseer's session type, and that artifact comments reach it).

F4. **Merge policy.** `main` is protected by a ruleset: pull requests only, squash merges, one approving review, review from the code owners for the tier-2 paths in `.github/CODEOWNERS`, required status checks (the CI jobs and the review gate), no bypass for agents (repository admins may bypass on pull requests only; cloud sessions act as the owner's account and so hold that bypass technically; the contract and a deny rule on the MCP merge tool keep them from merging). Tier 0 and tier 1 PRs merge unattended: `.github/workflows/review.yml` runs the code and numerics lenses (which PRs get which, and the briefs it reads from the base branch: its header) and its gate job approves or requests changes as `github-actions[bot]`; the PR author enables auto-merge after opening the PR, and GitHub merges and deletes the branch when the requirements are met. Tier 2 PRs from the factory app wait for the owner's approval in addition; tier 2 PRs authored by the owner's account do not, since GitHub does not ask an author to approve their own change (observed on #20). Interactive sessions are steered by the owner anyway; unattended sessions keep such PRs in draft for the owner; the gate labels every reviewed tier-2 PR `tier-2`, and the digest lists the merged ones. That is visibility, not a technical block: a cloud session is the owner's account, so nothing on GitHub tells the two apart. Two repository settings are prerequisites: "Allow GitHub Actions to create and approve pull requests" (the gate's approval) and the ruleset's dismissal of stale approvals on push (so a new commit is reviewed again before it can merge). Identities: local factory sessions act on GitHub as the GitHub App `particlemesh-factory[bot]` (one-hour installation tokens, the app installed on this repository only, no Workflows permission, so local agents cannot change CI; cloud sessions can, and workflow files are a code-owner path), which keeps the owner's reviews and comments distinguishable from agents'; cloud sessions act as the owner's account through Anthropic's GitHub proxy, which passes REST only (what sessions do about it: `CLAUDE.md`). The package manager's schedule and its handling of Dependabot PRs are in `.claude/agents/package-manager.md`. Minor review findings do not get pull requests of their own: the gate collects them in one `follow-up` issue per PR, the janitor (`.claude/agents/janitor.md`) takes the mechanical items, and the planner the rest. The overseer's digest reports what merged, and a revert is one PR.
