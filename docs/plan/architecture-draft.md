# ParticleMesh: architecture draft

Companion to `landscape-and-requirements.md`. Status: design record; §0 and the goals and decisions in `docs/goals/` are binding; §0 is derived work and changes through pull requests like any other plan text, while `docs/goals/` changes only with the owner.

Constraints:
- keep a symbolic-numeric angle possible without blocking on it;
- start with Cartesian 2D, reach multi-GPU 3D eventually, quasi-3D RZ optional;
- about 3 parameters with ForwardDiff first; find out later where Enzyme and Reactant help;
- prototype on the local RTX 4080 SUPER, produce on rented datacenter GPUs (MI300X or NVIDIA instances, through EDM's campaign backends);
- objective design and gradient-versus-Bayesian are discussed separately (not covered here);
- long term (A9) a generic particle–mesh framework and a showcase and stress test for Julia and Reactant compiler technology, with modular physics, a path to EDM integration and possible connections to Molly.jl; LWFA is the first physics module, not the definition of the package (§0).

Prior work this builds on (ElectronDynamicsModels.jl): MTK component models compiled to eight ODEs, KernelAbstractions kernels portable across NVIDIA and AMD, electron sharding across eight datacenter GPUs at 98% kernel efficiency, the Landau–Lifshitz force generated symbolically for any field, the run-manifest provenance layer, and the outlook naming differentiability of the field kernels as the next step.

## 0. Scope: a generic particle–mesh framework

Scope (A9): long term the package is a showcase and stress test for Julia and Reactant compiler technology, the physics is modular so it can be extended and perhaps integrate with EDM, and connections to packages such as Molly.jl are worth exploring. All of it is long term. The near-term plan (2D LWFA, ForwardDiff with about three parameters, KernelAbstractions on the 4080) stands. What changes now is only what would be expensive to retrofit: the split between engine and physics modules, the rules that keep the Reactant path open, and the name.

### 0.1 Engine and physics modules

The engine owns what every particle–mesh method shares: particle sets (SoA, fixed capacity, alive mask, cell sorting and compaction), structured grids with staggering and guard cells, the two transfers particle→mesh (deposition) and mesh→particle (gather) with shape functions, mesh operators (stencils, FFT-based solves), the time-loop harness, the diagnostics machinery (saving and callbacks; the physical quantities are the module's), checkpointing, the parallel exchange, and the differentiation and backend machinery. A physics module supplies the specific content: which quantities are deposited, which mesh equations are solved, which force acts on a particle and which pusher integrates it, which sources and boundaries exist.

| Module | Deposit | Mesh solve | Gather / force | Pusher | Status |
|---|---|---|---|---|---|
| Electromagnetic PIC for laser–plasma (LWFA) | current (Esirkepov), optionally charge | Yee FDTD, moving window, antenna, absorbing layers | E, B at the particle; Lorentz force | Boris | first module, phases 1–3 |
| Electrostatic PIC | charge | Poisson (FFT or LinearSolve) | E; electrostatic force | leapfrog / Boris | cheap second module: the JAX-in-Cell and ParticleInCell.jl benchmark set, and the CI-sized proof that the split is real |
| Test particles in prescribed fields | none | none (analytic fields from LaserTypes.jl / EDM evaluators) | MTK-generated forces incl. radiation reaction | Boris or per-particle RK | the EDM integration path (L3); first as the "external field" source inside the LWFA module |
| Envelope (ponderomotive) laser | susceptibility | envelope equation plus Yee for the wake | ponderomotive force, |a|²-corrected γ | modified Boris | phase 5 (B2) |
| Pairwise and P³M corrections | charge (long-range part) | Poisson / Ewald mesh part | mesh force plus short-range pairwise force | Verlet family | the Molly.jl bridge, long term (§0.3) |

Only the LWFA module has a schedule. The table exists so that the engine's interfaces are shaped by more than one module from the start, which is the cheap part; writing the electrostatic module early is also cheap and is the best test that the split holds.

Interface sketch. The main integration goal is SciML (A9); Molly compatibility is a nice-to-have, not a design driver (§0.3). So the container is a problem-like object that SciML can `solve` through the `DiscreteProblem`/`FunctionMap` harness (§0.6), parameters follow the SciML conventions (`p`, MTK parameter identities, `remake`), diagnostics are callbacks or saved states, and the reduced models of the ladder are ordinary SciML problems. Within that frame the vocabulary is close to Molly's, because both are particle codes: a container holding species, grids and fields; "interactions" as the pluggable unit in three kinds: mesh-mediated (deposit → solve → gather, the PIC kind), pairwise (short-range, needs a neighbour structure, the MD kind) and external (analytic fields and forces, the EDM kind); a `step!` that composes them; loggers for diagnostics; a simulator type that owns the time loop. Element type `T`, dimension `N` and the array type (hence the backend) are type parameters of the container, as decided in A8; unit handling stays in the user layer (A1), which also matches Molly's experience that units and differentiable simulation do not mix.

### 0.2 The compiler showcase and stress test

The same kernel source should run on three execution paths: (i) KernelAbstractions native on CUDA and ROCm, the production path of phases 1–3; (ii) Reactant, where the same KA kernels are traced, raised to StableHLO, fused with the surrounding array program, sharded across devices and differentiated by Enzyme-MLIR; (iii) Enzyme on the native path.

Verified mechanism (Reactant 0.2.289 sources; 0.2.303 registered): `ReactantKernelAbstractionsExt` defines `ReactantBackend <: KA.GPU`; `KA.get_backend` of a traced or concrete Reactant array returns it; a kernel launch inside `@compile` is captured through `Reactant.ka_with_reactant`; CUDA.jl must be loaded for kernel compilation even without an NVIDIA device; raising is automatic on TPU and opt-in (`raise=true`) elsewhere; AD of kernels inside Reactant works only on raised kernels (`raise=true, raise_first=true`); the docs state that not every class of kernel is raisable yet. Sharding needs the IFRT runtime preference, `Sharding.Mesh` plus `NamedSharding`, arrays created with `to_rarray(; sharding)`, communication inserted by the compiler, one compiled function per sharding, multi-host supported.

The precedent is Oceananigans: `OceananigansReactantExt` defines the `ReactantState` architecture whose `device` is Reactant's `ReactantBackend`, and its `Distributed(::ReactantState)` builds a `Sharding.Mesh` over `(:x, :y[, :z])`; DJ4Oceananigans (JuliaCon 2026) reports accurate Enzyme+Reactant gradients on several configurations and runs on CPU, GPU and TPU; the FOSDEM talk shows the model retargeted to thousands of TPUs. Oceananigans is a stencil code. A particle–mesh code stresses exactly what stencils do not:

- data-dependent indexing in gather and deposition (scatter with collisions: atomics on the native path, scatter-add or sort plus segmented reduction on the raised path);
- sorting, compaction and injection at fixed capacity (dynamic particle counts expressed through masks and a count scalar, no `push!` or `resize!` inside a traced step);
- the moving window (index shift of fields, refill at the front) and, under sharding, particle migration between shards next to halo exchange;
- mixed precision and compensated accumulation;
- reverse mode through scatter and gather over a long loop with checkpointing (the open Reactant regressions #3589, #3550, #3276 sit precisely here);
- compile time of a full step with a dozen kernels.

Deliverable of this angle: a particle-workload benchmark and correctness suite (gather, both deposition variants, sort and compaction, window shift, halo plus migration, one full step, one gradient) run on KA-CUDA, Reactant-CUDA and Reactant-CPU, with results recorded as run records in the trace graph and failures turned into upstream issues with minimal reproducers. It has value for the Julia ecosystem independent of the LWFA result, the way Oceananigans serves as Reactant's stencil benchmark.

### 0.3 Molly.jl: a nice-to-have compatibility target, not a design driver

Decision (A9): the main integration goal is SciML; Molly compatibility is a nice-to-have, kept in case other interesting physics comes up; do not design around it. What follows is therefore reference material and a list of things not to preclude.

Molly 0.23.3 (verified from its documentation and its sources): `System` holds `atoms`, `coords`, `velocities`, `boundary`, `pairwise_inters`, `specific_inter_lists`, `general_inters`, `neighbor_finder`, `loggers`, `constraints`; general interactions implement the AtomsCalculators `forces!` interface and `System` implements the AtomsBase `AbstractSystem` interface; simulators (`VelocityVerlet`, `Langevin`, ...) run through `simulate!`; the backend follows the array type (a CUDA fast path in `MollyCUDAExt`, a KernelAbstractions path for all backends); long-range electrostatics are the `Ewald` and `PME` general interactions, and PME is itself a particle–mesh method with KA kernels; reverse-mode differentiable simulation goes through `MollyEnzymeExt` with `autodiff(set_runtime_activity(Reverse), loss, ...)`, forward mode exists, memory is named as the limit (Checkpointing.jl suggested), loggers are ignored by AD, units are unsupported in differentiable runs, velocity Verlet in NVE gives exploding gradients, adjoint sensitivity is not available, and the stated golden rule is to check against finite differences.

To take now: the container / interaction / simulator / logger vocabulary, the array-type-selects-backend convention, and Molly's AD lessons (chunked losses, loggers outside the differentiated path, finite-difference checks as a gate) for L2. To explore later: (a) exposing a particle–mesh field solve as an AtomsCalculators general interaction so Molly can use it as a long-range solver, and conversely using Molly's pairwise interactions and neighbour finders as the short-range part of a P³M scheme here; (b) a shared benchmark on deposition and gather kernels, since PME and PIC deposition are the same operation; (c) whether a species here can present an AtomsBase-compatible view. None of it is scheduled; it is recorded so the interfaces do not preclude it.

### 0.4 Rules that keep the Reactant path open at no cost

1. Static shapes: fixed-capacity particle buffers, an alive mask and a count; injection and the moving window write into free slots; compaction is a stable partition within the same buffer. No data-dependent allocation inside `step!`.
2. The step is a pure function of (state, parameters) with its buffers passed explicitly: no globals, no host-side branching on device data (branch on static configuration only).
3. Both deposition variants are first-class and tested for equality: atomics (native fast path) and sort plus segmented reduction (deterministic, raisable). The raised path may also use scatter-add; its determinism is a measurement, not an assumption.
4. Scalar indexing never appears outside kernels; allocations go through `similar` or `KernelAbstractions.allocate`, so Reactant's traced `allocate` applies.
5. Reference kernels use only patterns the raiser handles: index arithmetic, loads and stores, scalar math; no shared-memory or warp-intrinsic tricks. Optimized native variants may exist behind the same interface.
6. Parameters are arrays or scalars of `T`, never baked into closures, so Enzyme-MLIR can see them.
7. A Reactant CPU smoke test runs in CI once Reactant is unparked (A9; §0.7 item 12): each kernel compiled with `@compile` and compared with the native CPU result, growing to one electrostatic and one electromagnetic step as those modules land. It needs no GPU, so the cloud sessions can run it. Until then no package depends on Reactant, and rules 1 to 6 keep every kernel ready for it. Once it runs, a failure in our kernel is fixed; a failure in Reactant itself, shown by the native CPU test of the same kernel passing, is parked as A9 prescribes (`docs/goals/A9-scope.md`): an `upstream` issue with a minimal reproducer, the test marked `@test_broken` with the issue number, and the Reactant feature it exercises left alone until upstream is fixed.
8. The AD strategy sits behind an interface (`jvp(step!, state, params, seeds)`, later `vjp`): the native path implements it with the tangent-bundle layout (§4), the Reactant path with Enzyme-MLIR forward mode on the raised program. User code does not see the difference.

Long term and unscheduled: TPU runs, multi-host sharding, reverse mode over the full loop on Reactant, P³M and Molly interoperability, EDM symbolic forces inside raised kernels (B6 extended: can an MTK-generated force be raised?).

### 0.5 Problem description separated from numerical implementation

Rationale (A10) for keeping the symbolic connection: it enforces a separation of concerns between the description of the problem and its numerical implementation. That turns the symbolic front-end (L3) from a door kept open into the mechanism behind a design principle: a physics module should be expressible as a problem description (species with their equations of motion and forces as MTK systems; the mesh equations as a `PDESystem` or an equation type; sources and boundaries as data), and the numerical implementation (shape functions, Yee versus FEM versus DG, pusher, deposition variant, backend) should be a separate choice that leaves the description untouched. Hand-written kernels remain the production path; the principle fixes what the kernel interfaces must look like so that generated code can replace them one slot at a time.

Numerical backends this admits for the mesh-solve slot, with an assessment:

- Yee FDTD as hand-written KA kernels (phases 1 to 3) and MOL's `staggered_groups` fused update (verified GPU-safe; §5 and the landscape notes).
- FEM through an expected MOL Ferrite backend (nothing public as of 2026-10-30, so timing is unknown; Ferrite 1.7.0 is the current release). Assessment: an unstructured FEM Poisson or Maxwell solve is what geometry-heavy electrostatic problems need (electrodes, structures), not what LWFA needs (structured box, moving window, GPU throughput, charge-conserving deposition matched to the Yee stagger); GPU assembly in Ferrite could not be verified. Value: a second mesh backend that proves the slot and the description/implementation split, for the electrostatic module; no role in the LWFA module.
- DG through Trixi.jl: the inspected copy (0.11.1; 0.17.18 registered) carries a 1D Maxwell equation type; DG-PIC is an established method family, but charge conservation and the particle–mesh coupling on DG meshes are a research topic of their own, and Trixi's GPU support (TrixiCUDA, CUDA-only, unregistered; a multi-GPU prototype) is not at the level of the KA path. Value: a third mesh backend and the precedent of `semidiscretize` turning a mesh solver into an `ODEProblem` right-hand side; not for the first module.
- Fast multipole as a mesh-free alternative for the long-range slot: FastMultipole.jl 2.3.0 (BYU FLOW Lab; Laplace kernel, CPU-parallel expansions, CUDA only for the direct interactions, ForwardDiff- and ReverseDiff-compatible per its README) and ExaFMMt.jl 0.1.2 (wrapper). Not needed for LWFA; relevant only if a pairwise or gravity module wants long-range sums without a mesh.
- TrixiParticles.jl 0.5.3 (SPH with KA kernels on NVIDIA, AMD and Apple per the March 2026 poster and the JuliaCon 2026 talk) and PointNeighbors.jl 0.6.7 (`GridNeighborhoodSearch` with `FullGridCellList` marked GPU-compatible, GPU support still "work in progress"): precedents for a KA particle framework whose coupled particle systems form one `Semidiscretization`, and a candidate neighbour search for the pairwise and P³M slot (§0.3) to compare with the engine's own cell sorting. SPH itself is a different physics (fluids whose particles carry the state) and enters only if a module wants it.

### 0.6 Time integration on Reactant: the harness ties the ladder together

`sciml-reuse.md` §1 wraps the hand-written step in a `DiscreteProblem` with `FunctionMap` (OrdinaryDiffEq) or `SimpleFunctionMap` (SimpleDiffEq), and the reduced models of the ladder are ODE problems. Two facts make this harness the natural Reactant entry point: SimpleDiffEq already runs under Reactant (prior work, to be reused), and OrdinaryDiffEq PR #4436 "Share ordinary solver paths with Reactant" (draft, opened 2026-08-30, updated 2026-10-17, 33 files) makes explicit solves inside Reactant compilation run the ordinary `solve!` loop with step control, with untraceable options (implicit algorithms, callbacks, `saveat`, user `tstops`, ...) throwing before tracing and an `OrdinaryDiffEqCoreReactantExt` for the traced primitives. So on the Reactant path the PIC step runs under `SimpleFunctionMap` or a `@trace` loop now, and under the shared OrdinaryDiffEq loop once #4436 lands (whether it covers `FunctionMap` is part of the B9 spike). The level-0 and level-1 reduced models run on Reactant through the same solvers, so the whole ladder, not only the PIC core, sits on the compiler path. Diagnostics then live outside the traced solve, as saved states or as reductions inside the step; Molly's lesson that loggers are ignored by AD applies.

### 0.7 Engine core contracts: who owns what

The engine core (`lib/ParticleMeshCore`) is cut into packages along these contracts. Each item names its owner, so two packages never freeze the same interface.

1. **Dimensions.** `N` is the number of resolved axes: `Grid{N}` for N = 1, 2, 3. Vector quantities always have three components (the "3V"), whatever `N` is; a 2D3V run is `Grid{2}` with three-component fields and momenta, and the collapsed axis is never stored. Particles carry one `Int32` cell index and one in-cell offset `T ∈ [0, 1)` per resolved axis, and three momentum components. One kernel source serves every `N` through `CartesianIndex{N}` and `Val{N}`; a kernel never branches on `N` at run time. Owner: the grid package.
2. **Fields.** The engine stores fields without knowing what they are. A `StaggeredField{T,N}` is one array with its stagger (a type-level `NTuple{N,Bool}`, true for a half-cell offset on that axis) and its guard width; a field set is a `NamedTuple` of them. A physics module declares its layout as a `NamedTuple` of staggers (`(Ex = (true, false), ...)` for the LWFA module, `(rho = (false,), phi = (false,))` for an electrostatic one), and the engine allocates from it. The grid package owns `StaggeredField` and allocation from a layout; the interface package owns the function by which a module hands its layout to the `System`. No component name appears in engine code.
3. **Topology and boundaries.** Each axis of a grid is `Periodic()` or `Bounded()`. Periodicity is topology and belongs to the engine; what happens at a `Bounded()` edge (absorbing layers, reflection, particle removal, the antenna) belongs to the module. Guard width is the maximum the module's shape order and stencils need, fixed at construction (`guard_width(shape)` from the shapes package, combined with the module's stencil width). On a `Bounded()` axis `fill_guards!` and `fold_guards!` leave the guard cells alone; the module's field boundary owns them. The first core packages may be periodic-only, as the 1D benchmark set is; `Bounded()` must exist as a type and be rejected with a clear error where not yet handled.
4. **Communication points.** Three, all engine-owned, all taking the grid (which carries the topology) and all no-op-capable on a single device: `fill_guards!(fields, grid, gstate)` copies interior values into the guard cells of periodic axes (and, later, from neighbouring ranks); `fold_guards!(fields, grid, gstate)` is its adjoint, adding guard-cell contributions from deposition back into the owning interior cells and then zeroing those guard cells, so that ⟨fill x, y⟩ = ⟨x, fold y⟩ holds exactly; both index through `idx` (item 10); `exchange_particles!(species, grid)` maps particles that left the local block back into it on periodic axes (and, later, sends them to neighbouring ranks). The grid package owns `fill_guards!`, the deposition package owns `fold_guards!` and tests it as the adjoint of `fill_guards!`, the species package owns `exchange_particles!`. A particle crossing a `Bounded()` edge is marked for the module's boundary handler, not wrapped: the alive mask is a `UInt8` status (0 dead, 1 alive, 1 + k for a particle that left through face k), and the interface package's hook `boundary!(module, species, grid)` runs right after `exchange_particles!`. A periodic axis has `n` cells and `n` points per component on every stagger; the grid package documents extents on bounded axes with the index helper.
5. **Particle buffers.** A species is a structure of arrays of fixed capacity with an alive mask and a device-side count. Between compactions, dead particles leave holes. After `compact!` (a stable partition within the same buffer), the alive particles occupy slots `1:count` in their previous relative order, and injection writes only into `count+1:capacity`. An injection that asks for more slots than are free writes as many as fit and adds the excess to a device-side overflow counter; the host reads that counter at diagnostic points and never branches on it inside a step. The species package owns the containers, loading and injection; the sort package owns `compact!`.
   Attributes: a fixed core set (cell `Int32` and offset `T` per resolved axis, three momentum components, weight, status), one vector per component, plus a module-declared `NamedTuple` of extra per-particle arrays (for example the previous position Esirkepov needs, filled by the module's push) and a `NamedTuple` of per-species constants (charge and mass, or mass alone), mirroring the field layout of item 2.
   Count: `count` is the high-water mark of occupied slots. A death sets only the status; `compact!` and `sort_by_cell!` reset `count` to the alive count; the alive count itself is a reduction taken at diagnostic points. Every particle kernel launches over the full capacity and checks the status, so no launch size depends on device data.
   Position advance: the species package owns a device function that advances (cell, offset) by a displacement in cell units, with a floor carry that keeps the offset in [0, 1) (including an offset that rounds up to 1 in Float32), and a generic `drift!` for its own tests and the interface package's mock module. Module pushers call the device function; `exchange_particles!` then wraps any displacement on periodic axes, and modules test their own CFL limits.
   Momentum: the engine stores momentum in the unit the module declares, and the loader's spread uses the same unit; u = p/(m_s c) per species is the proposal for the electrostatic and LWFA modules, to confirm when the first module is cut.
   Weights: a weight is n(xₚ)/ppc in units of n_c (Smilei's convention). `deposit!` adds w·q·S to each node with no volume factor, so the deposited field is a density and the sum over nodes is Σ wᵢqᵢ. The deposited `quantity` is a per-particle extra array or a species constant. The density is an isbits callable n(x, p) with the parameters passed explicitly (A3, §0.4 rule 6), with x in c/ω₀ computed from the global cell index and the offset.
   Loading: random numbers come from an in-house Philox4x32-10 device function. Key = (seed, stream id), using its two-word key; counter = (global cell index per axis, zero-padded to three words, then one word packing the slot within the cell in the high 16 bits and the draw index in the low 16, with an error when ppc or the draws exceed that; stream id = (species index, purpose)), so the moving-window refill draws the same numbers for the same global cell on every backend (A4). The known-answer vectors come from the Random123 distribution's `kat_vectors` file or from Random123.jl's tests, with the source cited, never written from memory; whether either is reachable from the sandbox is unverified. Quiet start places particles on a per-cell lattice, weights come from the density at the particle positions (A3), and Gaussian momenta come from Box–Muller over counter-based uniforms (`log`, `sqrt`, `sincos` from Base, generic in `T`; no SpecialFunctions).
6. **Sorting.** `sort_by_cell!` reorders the species storage in place, stably within a cell, applying one permutation to every SoA array, and writes the cell segment offsets into a buffer the caller owns. The sort key is cell · capacity + slot (`Int64`), with cell the column-major `LinearIndices` over the interior local cells and dead particles keyed at prod(n) + 1, exported as a helper the deposition package uses; it is a total order, so the result is stable and deterministic whatever sort algorithm runs and whatever the thread count; the sort package verifies AcceleratedKernels' sort on the CPU against that, and raisability stays with B9. Dead particles get a key past the last cell, so a sort also compacts and the offsets cover alive particles only. Sorted deposition takes a species already sorted and its offsets; it never sorts on its own. The sort package owns both the permutation and the offsets; its scratch (keys, permutation, a temporary column) is a workspace per item 17.
7. **Static configuration.** Branching is allowed on static configuration only (§0.4 rule 2), and that configuration lives in types: the deposition mode is `Reference()` (sort plus segmented reduction, deterministic) or `Fast()` (atomics), a type parameter of the `System`, and kernels dispatch on it. The deposition package defines the two mode types and `deposit!(mode, ...)`; the interface package carries the mode in the `System`. No globals.
8. **Accumulation trait.** `accumulation(::Type{T})` returns `Atomic()` for primitive floats and `Sorted()` for every other type, so Double32, Double64 and `Dual`-valued arrays take the sorted path with no type-specific code. ParticleMeshCore contains no ForwardDiff or DoubleFloats code and no extension for them: generic code runs with duals as it is. Component-wise atomics for duals happen in the tangent-bundle layout of §4, where every tangent is its own primitive array; a `Dual` element type appears only in the A8 test matrix, where the sorted path is enough. In `Fast()` mode a type whose trait is `Sorted()` still deposits through the sorted path, and the step sorts first; both choices are static. The deposition package owns the trait.
9. **Element types in tests.** The A8 matrix (Float32, Float64, Double32, `Dual{Float32,3}`) runs with `T` as the element type of every array, particles and fields alike: this tests that the kernels are generic. The tangent-bundle layout of §4 (value arrays plus P tangent arrays) is the later production layout for forward mode, built in the differentiation layer behind the `jvp` interface; core packages neither build it nor preclude it. Double32 may be marked broken where DoubleFloats lacks something a kernel needs (A8: drop it rather than work around it), with the missing function named.
10. **Moving-window hooks.** The window itself (B1) is a later package. The core only fixes the layout it needs. The grid splits into a static part (extents, spacing, guard width, topology), which lives in the `System`, and a dynamic `GridState` (per-axis global index of the first local cell, later the ring-buffer origin, and the step counter, with t = n·dt), a small device-side integer array in `State` so that a window advance changes data, not types, and does not recompile under Reactant. Particle cell indices are local to the block, and every field access in a kernel goes through the grid's index helper `idx(grid, gstate, I)`, never through raw array offsets; the grid package defines it now with a zero offset. The window package can then choose a ring buffer or a memory shift without touching any kernel.
   Conventions the grid package fixes and documents: local cells are 1-based and the global index is 0-based; the in-cell offset is measured from the lower unstaggered node; one symmetric guard width per grid, as a type parameter; spacing stored as `T`; face k = 2(axis − 1) + 1 for the low side and + 2 for the high side (the species status of item 4 uses it).
11. **The step and the harness.** `step!(system, state, params)` is a pure function of state and parameters with its buffers passed explicitly (§0.4 rule 2); the interface package owns it and proves it with a physics-free mock module. `System` is the static part (grid, module, deposition mode, shape, layouts, time step); `State` is fields, species, the `GridState` of item 10 and device-side counters; workspaces are separate (item 17). The harness package, in a package extension triggered by SciMLBase and RecursiveArrayTools, first verifies that `FunctionMap` accepts mixed element types (`Int32` and `T`), then gives `State` a zero-copy `ArrayPartition` view and back, plus `copyto!`, so it can serve as a `DiscreteProblem` state; the interface package touches no `Project.toml`. The harness copies the previous state into the next before the in-place step, which is the doubling A7's memory budget counts. `run!` is the plain loop around `step!` for tests. The `DiscreteProblem`/`FunctionMap` harness of §0.6, with `remake` and saved states, is its own package after the interfaces, in a SciMLBase package extension.
12. **Reactant smoke test.** It lives in its own workspace member, `lib/ParticleMeshReactant` (its tests are the smoke test now and the stress-test suite of §0.2 later), so Reactant and CUDA.jl load nowhere else; they still constrain resolution of the whole workspace, which shares one manifest (F1), and that is why KernelAbstractions is held at 0.9 (item 19). The grid package creates it, with `fill_guards!` as a KA kernel and a compare helper (Float32 and Float64; duals and Double32 on the Reactant path are B9). It first checks with a trivial kernel that a default `@compile` runs a KA kernel on the Reactant CPU client; if the CPU needs `raise=true`, it uses that and records why, and does not park our kernels over it. Every later core package that adds a kernel adds that kernel to it, compiled with the options the grid package recorded (one shared `compile_opts` in the compare helper): compiled with `@compile` (default options, no `raise`) and compared with the native CPU result. The full electrostatic step joins it when the electrostatic module exists, the electromagnetic step when the LWFA module does. Raising, Enzyme on the raised program and compile-time measurements belong to B9. Reactant needs CUDA.jl loaded to compile kernels even without an NVIDIA device (§0.2), so the smoke-test environment lists CUDA.jl; it is loaded, never asked for a device. Whether Reactant loads on Julia 1.13 is unverified (the registry compat allows it); if it fails at test time, that is parked as A9 says, as is any other failure caused by Reactant itself. If it does not even resolve or precompile, `lib/ParticleMeshReactant` leaves the workspace's `projects` list and becomes its own environment with its own manifest, so the rest of the workspace still instantiates; that departs from F1 and is recorded as a question for the owner (`questions/reactant-outside-workspace.md`).
13. **Allocation.** "No data-dependent allocation inside `step!`" (§0.4 rule 1) is tested as allocation that does not grow with particle count or grid size: `@allocated` at two sizes after warm-up, compared. Not as zero bytes, since a KernelAbstractions launch on the CPU backend may allocate a fixed amount.
14. **Engine kernels and module kernels.** The engine owns what does not know the physics: shape functions, `gather!` of any field set, scalar deposition of a module-supplied per-particle quantity (`deposit!(mode, field, species, shape, quantity)`, both modes), sorting, compaction, loading, the communication points and the step harness. The "mesh operators" of §0.1 are generic helpers (a stencil launcher over a field set, an FFT plan wrapper) that the engine may add when a second module needs them; the equations are the module's. A module owns its pusher, its mesh solve (Yee, Poisson), its filter, its current deposition and its diagnostics. Esirkepov is the LWFA module's (`lib/Wakefields`), built on the engine's shape weights; its charge-conservation test belongs there. The electrostatic module (`lib/ParticleMeshElectrostatic`) writes its own pusher. The engine's generic pusher hook is `push_particles!(module, ...)`; no kernel is named `push!`, which would extend `Base.push!`.
15. **Shapes and gather.** A shapes package after the grid package, in parallel with the species package, owns the shape types (`Shape{1}`, `Shape{2}`, optionally `Shape{3}`, as type-level static configuration per item 7), `guard_width(shape)`, the weights at a stagger, and the device-level gather at `(cell::NTuple{N,Int32}, offset::NTuple{N,T})` that module kernels inline; it tests them on plain tuples and knows no species. The species-level `gather!(out, fields, species, shape, grid, gstate)`, which writes into a workspace `NamedTuple` named like the field set, belongs to the deposition package, which depends on shapes and species and owns the gather/deposition adjoint test; it reuses the same weights, so gather and deposition are adjoint by construction.
   Signatures the deposition package fixes: `deposit!(mode, field, species, shape, quantity, grid, gstate, ws)`, where `ws` holds the sort's segment offsets and the `DiffCache` scratch; `deposit!` accumulates into its target, and the step zeroes the deposited fields once per step before the first species deposits. `accumulation` is applied to the target field's element type, the type the atomics act on.
16. **Element types per array.** A field set may hold a different element type per component, and `deposit!` accumulates in the element type of the target field, so B5 can later keep accumulators in FP64 with FP32 particles. Allocation from a layout takes one `T` or a `NamedTuple` of element types keyed like the layout. Kernels never assume that field and particle element types are equal; the tests use one `T`, as item 9 says.
17. **Buffers and workspaces.** Every scratch buffer is allocated once, outside `step!`, by the package that needs it, and passed in (§0.4 rule 2). Scratch buffers of element type `T` (deposition and gather scratch) are PreallocationTools `DiffCache`s, read with `get_tmp(cache, u)`, with the chunk size set in the `System`, so a `ForwardDiff.gradient` over parameters does not allocate inside the step; a mismatched chunk size would reallocate, which item 13's test catches. The `State` itself is built in the `Dual` type for a gradient, since the weights depend on the parameters (A3); it is not a `DiffCache`. Index buffers (keys, permutations, segment offsets, counters) are plain integer arrays. PreallocationTools is a direct dependency of ParticleMeshCore (ForwardDiff is only its weak dependency). Unverified: `get_tmp` on Reactant traced arrays (the smoke test covers it) and on device arrays inside a KA launch (it is called on the host before the launch).
18. **Tests and tolerances (A7).** Physics errors are caught by exact identities, held to `C·eps(T)` scaled by problem size and step count, at two or more sizes for every `T` in the A8 matrix:
   - grid: `fill_guards!` reproduces a periodic function exactly;
   - shapes and gather: partition of unity; constant and linear fields reproduced exactly on every stagger (B-spline shapes reproduce degree 0 and 1 only); for a quadratic field and a degree-p shape with p ≥ 2, the gathered value is f + (p+1)h²f''/24, which the test checks as a known shift, or against the analytically convolved field;
   - deposition: `fold_guards!` is the adjoint of `fill_guards!`, ⟨fill x, y⟩ = ⟨x, fold y⟩; total deposited quantity equals Σ wᵢqᵢ; deposition is the adjoint of gather; the atomic and sorted variants agree per node;
   - sort and compaction: the result is a permutation of the input, bitwise, with offsets summing to the count; compaction preserves order;
   - species: free streaming in zero fields is exact up to the cell and offset split; the periodic wrap conserves the count exactly; the Philox known-answer vectors match;
   - reference mode: bitwise equal across reruns and across `JULIA_NUM_THREADS` = 1 and many on the CPU backend. Agreement across backends (CPU, CUDA, Reactant) is a measured tolerance, not a bitwise property.
   The first core package creates `lib/ParticleMeshCore/test/tolerances.toml` and a shared test helper module (`roundoff_bound(T; n, steps, C)`, the A8 type-matrix loop, `fd_scan(f, x; hs)` for finite-difference step scans). Each package measures its residuals, records the measured maxima and a proposed `C` there marked "proposed", and its tests use that `C`; the PR lists the proposals, and merge does not wait for the owner, who accepts a value by moving it into A7. Dual tests in the core check that the value part equals the primal run bitwise in reference mode and that partials match exact derivatives where the map is linear (deposition in the weights); finite-difference comparisons run only in Float64 with a step scan, reporting the scan's error floor.
   CI: the root `test/runtests.jl` includes each `lib/*/test/runtests.jl` except the Reactant one, and the root `test/Project.toml` lists the `lib/` packages through `[sources]` plus the A8 test dependencies (ForwardDiff, DoubleFloats), so `julia-runtest` covers them with no workflow change. `lib/ParticleMeshReactant` runs in CI's `reactant` job ("Reactant CPU smoke test"), which already exists: it passes trivially until `lib/ParticleMeshReactant/Project.toml` appears, then instantiates the workspace at the root and runs that member's `Pkg.test()` on Julia 1.13. The package that creates the member needs no workflow change. If the member has to leave the workspace (item 12's fallback), the job's instantiate step no longer covers it; that PR says so, and the owner adjusts the job from outside the factory.
   Shared files: each core package has its own test file, `lib/ParticleMeshCore/test/<package>.jl` and `lib/ParticleMeshReactant/test/<package>.jl`; the grid package creates both `runtests.jl` files with an include list, and each later package appends one line. `tolerances.toml` keeps one table per package, and each package uses the test-id range its work package assigns, so packages in parallel do not collide.
   Budgets: A7's throughput budget is defined on the GPU; a CPU core package records timings without a threshold, states item 13's allocation test, and proposes a CI-time budget marked unverified.
19. **Bootstrap.** The grid package creates `lib/ParticleMeshCore`, adds it and its test environment to the root workspace, and adds the core dependency set at once (KernelAbstractions, Atomix, Adapt, AcceleratedKernels, PreallocationTools), so later core packages touch only source and test files; the exception is the harness package, which adds SciMLBase and RecursiveArrayTools as weak dependencies with an extension (tier 2) and OrdinaryDiffEqFunctionMap or SimpleDiffEq as test dependencies. It resolves that set together with Reactant and CUDA.jl before writing compat entries: Reactant 0.2 caps KernelAbstractions at 0.9 (registry checked 2026-10-31; KA itself is at 0.10.4), so CUDA.jl resolves to 6.2–6.4 (6.5 needs KA 0.10) and AcceleratedKernels to 0.5; the CUDA compat in `lib/ParticleMeshReactant` must admit 6, so the core's compat is `KernelAbstractions = "0.9.43 - 0.9"` (AcceleratedKernels needs 0.9.43) and the kernels are written against the KA 0.9 API. It records the resolved versions in its PR.
20. **Order.** grid (bootstrap and `lib/ParticleMeshReactant`) → shapes and species, in parallel → sort (needs species) → deposition (`gather!` and `deposit!`; needs shapes, species and the sort's offsets for `Reference()`) → interface (`System`, `State`, `step!`, with B10 first) → harness. Each work package is assigned a test-id range. That package edits `/Project.toml` and `/lib/*/Project.toml`, which are tier 2 (`.github/CODEOWNERS`).

## 1. Layering

The rule: the hot loop is plain numeric kernels over typed arrays; everything symbolic generates code that plugs into those kernels, never the other way around. That is the EDM pattern applied to a grid code.

```
L4  Optimization / campaigns     Optimization.jl, BO baseline, run manifests, cloud (EDM backends)
L3  Symbolic front-end (opt.)    MTK particle models → force kernels; MOL staggered groups → Maxwell update;
                                 LaserTypes.jl / Symbolics expressions → laser & density kernels; parameter identities
L2  Differentiation              tangent-bundle layout (value + P tangents), Dual-number push, per-component atomics;
                                 Enzyme forward/reverse on kernels; Reactant path: same KA kernels traced, raised, sharded (smoke test from day one)
L1  Parallel layout              Grid{N} with guard cells, slab/block decomposition, halo + particle exchange,
                                 moving window as a global shift; single device → multi-device node → MPI
L0  Core numerics                SoA fields and particles, KernelAbstractions kernels: gather, push, deposit,
                                 Yee E/B, filter, inject, absorb; dims-generic via Val{N}; physics modules plug in via §0.1
```

L0 and L1 have no symbolic dependency and are the first deliverable. L3 is an optional package extension that reuses EDM. The engine/module split of §0.1 cuts across the layers: the engine is the L0–L2 machinery, a physics module is a set of L0 kernels (and, through L3, their generators) plugged into the interaction interfaces.

## 2. Core numerics (L0)

Data layout
- Fields: one `AbstractArray{T,N}` per component, its stagger carried as a type-level tuple, guard cells sized by the shape-function order (§0.7 items 2 and 3). The components are the module's: the LWFA module declares Ex, Ey, Ez, Bx, By, Bz, Jx, Jy, Jz and optionally ρ with Yee staggers. In 2D3V all field and momentum components exist and vary only along the two resolved axes, as in Smilei and PIConGPU; the grid is `Grid{2}` and the collapsed axis is not stored (§0.7 item 1), which keeps one kernel source for N = 1, 2, 3.
- Particles (per species): SoA buffers with `cell::Int32` per resolved axis plus an in-cell offset `T` in [0, 1) per resolved axis, momentum `T × 3`, weight, alive mask, optional tag (§0.7 item 5). The cell+offset split is what keeps FP32 usable over a long moving window (PIConGPU layout); FP32 is required on the 4080 SUPER (FP64 at 1/64 rate), FP64 is available on rented datacenter GPUs (MI300X, NVIDIA data-center cards). `T` is a type parameter throughout and is chosen at the user level; nothing assumes Float64 or Float32. The same kernels must run with Float32, Float64, DoubleFloats (Double32 is the useful one on consumer GPUs, since it keeps FP32 throughput) and ForwardDiff duals; the deposition kernel selects its accumulation path by a trait on `T` (atomics for primitive types, the sorted segmented reduction for every other type (§0.7 item 8)). See `docs/goals/A8-element-type.md`.
- Fixed-capacity buffers with periodic compaction and cell sorting (supercells). Sorting also enables a deposition variant without atomics (segmented reduction), which matters for the Reactant path and for deterministic bitwise reproducibility.

Kernels (KernelAbstractions, `foreachindex` style as in EDM)
- `gather!`: tensor-product shape functions (order 2 or 3; order 1 only for tests, its kinks hurt gradients), per-component staggering.
- `push_particles!` (the module's hook, §0.7 item 14): Boris by default in the LWFA module; the force term is a pluggable callable so that L3 can substitute an MTK-generated force (Lorentz + Landau–Lifshitz, later quantum corrections). For non-Lorentz forces a generic RK/implicit per-particle step replaces Boris.
- `deposit_current!`: Esirkepov in N-D (implement the 3D formula, specialize the collapsed axis), atomics only on primitive components (duals component by component), the sorted path otherwise (§0.7 item 8).
- `yee_E!`, `yee_B!`: curl stencils over guard cells; Lehe or PSATD solver later for numerical Cherenkov.
- `filter!` (binomial), `absorb!` (PML or simple damping layers), `inject!` (plasma at the window front, laser antenna at a plane), `window_shift!`.
- Time loop: `step!` is the unit. Tests drive it with `run!`, a plain loop; runs drive it through the `DiscreteProblem`/`FunctionMap` harness of §0.6, which supplies saved states and `remake`. No ODE integrator acts inside the step: the harness only calls it at fixed steps (§0.7 item 11).

Validation targets: Landau damping, two-stream, Weibel (JAX-in-Cell set), 1D wake against the analytic nonlinear wake, 2D LWFA against Smilei and PIConGPU (containerized setups exist), energy and charge conservation.

## 3. Parallel layout (L1): 2D now, multi-GPU 3D later

- `Grid{N}` carries a global extent, a local block, and guard regions. Single-device runs use the same code with a no-op exchange.
- Decomposition: start with a 1D slab decomposition along the propagation axis. It matches the moving window (ranks form a ring; the window advance is a whole-cell shift where the front rank injects and the back rank drops), keeps halo exchange one-dimensional, and already covers one node of eight GPUs. 3D block decomposition and load balancing (particles concentrate in the bubble and bunch) come after.
- Exchange primitive: `fill_guards!(fields, grid, gstate)`, its adjoint `fold_guards!(fields, grid, gstate)` after deposition, and `exchange_particles!(species, grid)` as the only communication points (§0.7 item 4); on a single device they implement periodic axes and nothing else. Implementations in order: none (single device); device-to-device copies between devices of one node driven by one Julia task per device (EDM's sharding pattern, generalized from "split the electrons" to "split the domain"); CUDA-aware MPI.jl for multi-node. ImplicitGlobalGrid.jl is a candidate for the structured-grid halo part (GPU-aware MPI, CUDA and AMDGPU); particle migration is ours.
- Vendor portability stays free through KernelAbstractions plus GPUDiagnostics.jl, so the MI300X cloud route remains open.
- Prototyping without a multi-GPU box: run the decomposition on the KA CPU backend with MPI on a many-core CPU, or several ranks on one GPU, before renting a multi-GPU instance.

### On skipping quasi-3D

RZ with azimuthal modes is a separate numerics path (cylindrical Maxwell, mode-decomposed deposition) that does not advance the multi-GPU 3D goal. The cost reducer that keeps Cartesian geometry and the same kernels is the laser envelope (ponderomotive guiding center) model: it removes the λ₀ resolution along the propagation axis, 10 to 30 times fewer cells, and the ponderomotive force is smoother than the resolved laser oscillation, which is good for gradients. Suggested path: 2D full PIC → 2D envelope → 3D envelope on one node → 3D full PIC for production checks. Validity (a₀ up to a few, pulse length much larger than λ₀) covers the LWFA regime of interest.

## 4. Differentiation (L2)

### Forward mode with about 3 parameters (phase 1)

- Tangent-bundle layout rather than `CuArray{Dual}`: every field and particle array exists as a value array plus `P` tangent arrays. Inside `push_particles!` and `gather!` the thread loads value and tangents into a local `ForwardDiff.Dual{Tag,T,P}`, does the arithmetic, and stores the components back. `deposit_current!` adds value and each tangent with separate primitive atomics, since atomics on `Dual` structs are not available. `P = 0` recovers the primal code with no overhead.
- Cost: memory and FLOPs scale as `P + 1`. A 2D run at 2048 × 512 cells, 16 particles per cell, FP32, P = 3 needs roughly 2 GB for particles, which fits the 4080.
- Which parameters are active is a setup-time decision (a₀, w₀ or τ, n₀, focus position, ramp length). Through L3 these are symbolic parameter identities, so "active parameter" is a tag on the MTK parameter and the tangent seeding is generated, not hand-written.
- Noise and non-smoothness (cell crossings, injection events) are discussed with the objective; the layout above is neutral to that discussion.

### Where Enzyme helps

- Enzyme forward mode with `BatchDuplicated` shadows over the same SoA layout could replace the hand-rolled Dual load/store with less code and possibly better register use. Worth a phase 2 comparison on `push_particles!`.
- Reverse mode becomes necessary when the parameter count grows (pulse shaping with 10 to 100 spectral coefficients, a spline- or network-parameterized density profile). Plan: `Enzyme.autodiff(Reverse, step!, ...)` per time step with a checkpointing schedule over the loop (store full state every k steps, recompute in between), custom rules for `deposit_current!` if Enzyme does not handle the atomics (its adjoint is a gather, easy to write by hand). Open Enzyme-on-CUDA bugs as of Oct 2026 (`cis` in kernels, `fill!`, tape types) are tracked in the landscape notes; none is a blocker for forward mode.
- Enzyme on MTK-generated scalar force functions is well-trodden; the L3 symbolic force is not a risk for AD.

### Where Reactant helps

- Reactant compiles whole Julia array programs to XLA with Enzyme-MLIR for both AD modes, supports `@trace` loops with automatic checkpointing, and has multi-device sharding. A PIC written as array operations (sort, segmented reduction for deposition, gather by indexing, stencil broadcasts) would get fusion, sharding and reverse mode in one go. That is the JAX-in-Cell route and the most direct bridge to the symbolic layer, because generated array code (including MOL's fused staggered update) can be traced.
- Risks as of Oct 2026: gather/scatter under reverse mode has open correctness and performance regressions, compile times, and control-flow restrictions. Since A9 Reactant is a declared long-term target, not an experiment, and the mechanism is verified (§0.2): the KA kernels are traced through `ReactantBackend` and raised, so no array rewrite is needed; the deposition kernel stays available in both atomic and sort-based forms so the raised path is a backend, not a rewrite; AD inside Reactant works only on raised kernels, so forward mode on that path is Enzyme-MLIR forward over the raised program, while the Dual layout above stays the native-path implementation behind the `jvp` interface (§0.4, rule 8). Whether `Dual`-valued locals inside a kernel survive raising is untested and part of the B9 spike. The first Reactant target is the 1D3V level, where parity with JAX-in-Cell is a day's work; Reactant on CPU needs no GPU, so a smoke test belongs in CI from the first package.

## 5. Symbolic front-end (L3): the door kept open

The principle this layer serves is stated in §0.5: the symbolic layer is how problem description and numerical implementation are kept apart, which is why it stays in the design even though hand-written kernels are the production path.

What EDM already gives, and how it maps onto PIC:

| EDM today | ParticleMesh use |
|---|---|
| `ChargedParticle(external_field, radiation_model)` composed from `ParticleDynamics`, `EMFieldDynamics`, forces | same components with a `GridField` input in place of `external_field`: E and B at the particle are kernel inputs; `mtkcompile` + `build_function` yield a device-callable force or RHS |
| Landau–Lifshitz generated for any field | radiation reaction in the pusher for free; quantum-corrected LL later as one more component |
| LaserTypes.jl fields, unit systems | laser antenna/initial fields and density profiles as symbolic expressions compiled to kernels; SI/natural units handled once |
| parameters via SymbolicIndexingInterface, tunables | the active-parameter set for the tangent layer |
| run manifests, campaigns, dashboard | unchanged |

On the grid side, MOL's `staggered_groups` with `scalarize_single_element_regions = false` produces resolution-independent fused-broadcast Yee updates that run on the GPU (measured 2026-10-30). It can be an alternative Maxwell backend behind the same `yee_E!`/`yee_B!` interface once (a) a constructor from the `System` avoids the O(N²) `DAEProblem` residual build (small MOL PR), (b) current sources and guard-cell exchange are added. ModelingToolkit #5139 would extend this to arbitrary array models; worth tracking, not worth waiting for.

What this buys: composable physics models, units, documentation value, and symbolic parameter identities for AD; what it costs: nothing on the hot loop, since the generated code is scalar per particle or fused per slice.
