# ParticleMesh: architecture draft

Companion to `landscape-and-requirements.md`. §0.1 to §0.6 and the goals and decisions in `docs/goals/` are binding, §0.7 holds the engine contracts written from the spike's code (A0) and the proposals still open; §0 is derived work and changes through pull requests like any other plan text, while `docs/goals/` changes only with the owner.

Constraints:
- keep a symbolic-numeric angle possible without blocking on it;
- start with Cartesian 2D, reach multi-GPU 3D eventually, quasi-3D RZ optional;
- about 3 parameters with ForwardDiff first; find out later where Enzyme and Reactant help;
- prototype on the local RTX 4080 SUPER, produce on rented datacenter GPUs (MI300X or NVIDIA instances, through EDM's campaign backends);
- objective design and gradient-versus-Bayesian are discussed separately (not covered here);
- long term (A9) a generic particle–mesh framework and a showcase and stress test for Julia and Reactant compiler technology, with modular physics, a path to EDM integration and possible connections to Molly.jl; LWFA is the first physics module, not the definition of the package (§0).

Prior work this builds on (ElectronDynamicsModels.jl): MTK component models compiled to eight ODEs, KernelAbstractions kernels portable across NVIDIA and AMD, electron sharding across eight datacenter GPUs at 98% kernel efficiency, the Landau–Lifshitz force generated symbolically for any field, the run-manifest provenance layer, and the outlook naming differentiability of the field kernels as the next step.

## 0. Scope: a generic particle–mesh framework

Scope (A9): long term the package is a showcase and stress test for Julia and Reactant compiler technology, the physics is modular so it can be extended and perhaps integrate with EDM, and connections to packages such as Molly.jl are worth exploring. All of it is long term. The near-term plan (2D LWFA, ForwardDiff with about three parameters, KernelAbstractions on the 4080) stands. What §0 fixes now is only what would be expensive to retrofit: the split between engine and physics modules, the rules that keep the Reactant path open, and the name.

### 0.1 Engine and physics modules

The engine owns what every particle–mesh method shares: particle sets (SoA, fixed capacity, alive mask, cell sorting and compaction), structured grids with staggering and guard cells, the two transfers particle→mesh (deposition) and mesh→particle (gather) with shape functions, mesh operators (stencils, FFT-based solves), the time-loop harness, the diagnostics machinery (saving and callbacks; the physical quantities are the module's), checkpointing, the parallel exchange, and the differentiation and backend machinery. A physics module supplies the specific content: which quantities are deposited, which mesh equations are solved, which force acts on a particle and which pusher integrates it, which sources and boundaries exist.

| Module | Deposit | Mesh solve | Gather / force | Pusher | Status |
|---|---|---|---|---|---|
| Electromagnetic PIC (`ParticleMeshElectromagnetic`) | current through the engine's charge-conserving `deposit_flux!` (Esirkepov), optionally charge | Yee FDTD, absorbing layers (PML later), binomial filter | E, B at the particle; Lorentz force | Boris | the self-consistent Maxwell–Vlasov module, phases 1–3; exists for N = 1 periodic (WP-014: Yee, relativistic Boris, the module's step, the three 1D cases), without boundaries or filter |
| Laser–plasma (LWFA, `Wakefields`), built on the electromagnetic module | as the electromagnetic module | as the electromagnetic module, plus the moving window and the laser antenna | as the electromagnetic module | Boris | first application, phases 1–3 |
| Electrostatic cases (Landau damping, two-stream, the JAX-in-Cell and ParticleInCell.jl set) | as the electromagnetic module | as the electromagnetic module, with no transverse fields | as the electromagnetic module | Boris | not a module (A9): edge cases of the electromagnetic module, as Smilei runs them; the 1D electrostatic spike of WP-010 is their first reference |
| Test particles in prescribed fields | none | none (analytic fields from LaserTypes.jl / EDM evaluators) | MTK-generated forces incl. radiation reaction | Boris or per-particle RK | the EDM integration path (L3); first as the "external field" source inside the LWFA module |
| Envelope (ponderomotive) laser | susceptibility | envelope equation plus Yee for the wake | ponderomotive force, |a|²-corrected γ | modified Boris | phase 5 (B2) |
| Pairwise and P³M corrections | charge (long-range part) | Poisson / Ewald mesh part | mesh force plus short-range pairwise force | Verlet family | the Molly.jl bridge, long term (§0.3) |

Only the LWFA module has a schedule. The table exists so that the engine's interfaces are shaped by more than one module from the start, which is the cheap part; the electromagnetic module is the proof that the split holds (A9), and the electrostatic cases test it in the limit of no transverse fields.

Interface sketch. The main integration goal is SciML (A9); Molly compatibility is a nice-to-have, not a design driver (§0.3). So the container is a problem-like object that SciML can `solve` through the `DiscreteProblem`/`FunctionMap` harness (§0.6), parameters follow the SciML conventions (`p`, MTK parameter identities, `remake`), diagnostics are callbacks or saved states, and the reduced models of the ladder are ordinary SciML problems. Within that frame the vocabulary is close to Molly's, because both are particle codes: a container holding species, grids and fields; "interactions" as the pluggable unit in three kinds: mesh-mediated (deposit → solve → gather, the PIC kind), pairwise (short-range, needs a neighbour structure, the MD kind) and external (analytic fields and forces, the EDM kind); a `step!` that composes them; loggers for diagnostics; a simulator type that owns the time loop. Element type `T`, dimension `N` and the array type (hence the backend) are type parameters of the container, as decided in A8; unit handling stays in the user layer (A1), which also matches Molly's experience that units and differentiable simulation do not mix.

### 0.2 The compiler showcase and stress test

The same kernel source should run on three execution paths: (i) KernelAbstractions native on CUDA and ROCm, the production path of phases 1–3; (ii) Reactant, where the same KA kernels are traced, raised to StableHLO, fused with the surrounding array program, sharded across devices and differentiated by Enzyme-MLIR; (iii) Enzyme on the native path.

Verified mechanism (Reactant 0.2.289 sources; 0.2.303 registered): `ReactantKernelAbstractionsExt` defines `ReactantBackend <: KA.GPU`; `KA.get_backend` of a traced or concrete Reactant array returns it; a kernel launch inside `@compile` is captured through `Reactant.ka_with_reactant`; CUDA.jl must be loaded for kernel compilation even without an NVIDIA device; raising is automatic on TPU and opt-in (`raise=true`) elsewhere; AD of kernels inside Reactant works only on raised kernels (`raise=true, raise_first=true`); the docs state that not every class of kernel is raisable yet. Sharding needs the IFRT runtime preference, `Sharding.Mesh` plus `NamedSharding`, arrays created with `to_rarray(; sharding)`, communication inserted by the compiler, one compiled function per sharding, multi-host supported.

The precedent is Oceananigans: `OceananigansReactantExt` defines the `ReactantState` architecture whose `device` is Reactant's `ReactantBackend`, and its `Distributed(::ReactantState)` builds a `Sharding.Mesh` over `(:x, :y[, :z])`; DJ4Oceananigans (JuliaCon 2026) reports accurate Enzyme+Reactant gradients on several configurations and runs on CPU, GPU and TPU; the FOSDEM talk shows the model retargeted to thousands of TPUs. Oceananigans is a stencil code. A particle–mesh code stresses exactly what stencils do not:

- data-dependent indexing in gather and deposition (scatter with collisions: atomics on the native path, scatter-add or sort plus segmented reduction on the raised path);
- sorting, compaction and injection at fixed capacity (dynamic particle counts expressed through masks and a count scalar, no `push!` or `resize!` inside a traced step);
- the moving window (index shift of fields, refill at the front) and, under sharding, particle migration between shards next to halo exchange;
- mixed precision and compensated accumulation;
- reverse mode through scatter and gather over a long loop with checkpointing (the open Reactant regressions #3589, #3550, #3276 sit precisely here);
- compile time of a full step with a dozen kernels.

Deliverable of this angle: a particle-workload benchmark and correctness suite (gather, both deposition variants, sort and compaction, window shift, halo plus migration, one full step, one gradient) run on KA-CUDA, Reactant-CUDA and Reactant-CPU, with a run manifest next to each result (F3) and failures turned into upstream issues with minimal reproducers. It has value for the Julia ecosystem independent of the LWFA result, the way Oceananigans serves as Reactant's stencil benchmark.

### 0.3 Molly.jl: a nice-to-have compatibility target, not a design driver

Decision (A9): the main integration goal is SciML; Molly compatibility is a nice-to-have, kept in case other interesting physics comes up; do not design around it. What follows is therefore reference material and a list of things not to preclude.

Molly 0.23.3 (verified from its documentation and its sources): `System` holds `atoms`, `coords`, `velocities`, `boundary`, `pairwise_inters`, `specific_inter_lists`, `general_inters`, `neighbor_finder`, `loggers`, `constraints`; general interactions implement the AtomsCalculators `forces!` interface and `System` implements the AtomsBase `AbstractSystem` interface; simulators (`VelocityVerlet`, `Langevin`, ...) run through `simulate!`; the backend follows the array type (a CUDA fast path in `MollyCUDAExt`, a KernelAbstractions path for all backends); long-range electrostatics are the `Ewald` and `PME` general interactions, and PME is itself a particle–mesh method with KA kernels; reverse-mode differentiable simulation goes through `MollyEnzymeExt` with `autodiff(set_runtime_activity(Reverse), loss, ...)`, forward mode exists, memory is named as the limit (Checkpointing.jl suggested), loggers are ignored by AD, units are unsupported in differentiable runs, velocity Verlet in NVE gives exploding gradients, adjoint sensitivity is not available, and the stated golden rule is to check against finite differences.

To take now: the container / interaction / simulator / logger vocabulary, the array-type-selects-backend convention, and Molly's AD lessons (chunked losses, loggers outside the differentiated path, finite-difference checks as a gate) for L2. To explore later: (a) exposing a particle–mesh field solve as an AtomsCalculators general interaction so Molly can use it as a long-range solver, and conversely using Molly's pairwise interactions and neighbour finders as the short-range part of a P³M scheme here; (b) a shared benchmark on deposition and gather kernels, since PME and PIC deposition are the same operation; (c) whether a species here can present an AtomsBase-compatible view. None of it is scheduled; it is recorded so the interfaces do not preclude it.

### 0.4 Rules that keep the Reactant path open at no cost

1. Static shapes: fixed-capacity particle buffers, an alive mask and a count; injection and the moving window write into free slots; compaction is a stable partition within the same buffer. No data-dependent allocation inside `step!`.
2. The step is a pure function of (state, parameters) with its buffers passed explicitly: no globals, no host-side branching on device data (branch on static configuration only).
3. Both deposition variants are first-class and tested for equality: atomics (native fast path) and sort plus segmented reduction (deterministic, raisable). The raised path may also use scatter-add; its determinism is a measurement, not an assumption.
4. Scalar indexing never appears outside kernels; allocations go through `similar` or `KernelAbstractions.allocate`, so Reactant's traced `allocate` applies.
5. Reference kernels use only patterns the raiser handles: index arithmetic, loads and stores, scalar math; no shared-memory or warp-intrinsic tricks. Optimized native variants may exist behind the same interface.
6. Parameters are arrays or scalars of `T`, never baked into closures, so Enzyme-MLIR can see them.
7. A Reactant CPU smoke test runs in CI once Reactant is unparked (A9; §0.7): each kernel compiled with `@compile` and compared with the native CPU result, growing to one step of the electromagnetic module as it lands, first on an electrostatic case with no transverse fields and then with the full fields (A9: there is no electrostatic module). It needs no GPU, so the cloud sessions can run it. Until then no package depends on Reactant, and rules 1 to 6 keep every kernel ready for it. Once it runs, its failures are handled as A9 prescribes: our kernel is fixed, Reactant itself is parked.
8. The AD strategy sits behind an interface (`jvp(step!, state, params, seeds)`, later `vjp`): the native path implements it with the tangent-bundle layout (§4), the Reactant path with Enzyme-MLIR forward mode on the raised program. User code does not see the difference.

Long term and unscheduled: TPU runs, multi-host sharding, reverse mode over the full loop on Reactant, P³M and Molly interoperability, EDM symbolic forces inside raised kernels (B6 extended: can an MTK-generated force be raised?).

### 0.5 Problem description separated from numerical implementation

Rationale (A10) for keeping the symbolic connection: it enforces a separation of concerns between the description of the problem and its numerical implementation. That turns the symbolic front-end (L3) from a door kept open into the mechanism behind a design principle: a physics module should be expressible as a problem description (species with their equations of motion and forces as MTK systems; the mesh equations as a `PDESystem` or an equation type; sources and boundaries as data), and the numerical implementation (shape functions, Yee versus FEM versus DG, pusher, deposition variant, backend) should be a separate choice that leaves the description untouched. Hand-written kernels remain the production path; the principle fixes what the kernel interfaces must look like so that generated code can replace them one slot at a time.

Numerical backends this admits for the mesh-solve slot, with an assessment:

- Yee FDTD as hand-written KA kernels (phases 1 to 3) and MOL's `staggered_groups` fused update (verified GPU-safe; §5 and the landscape notes).
- FEM through an expected MOL Ferrite backend (nothing public as of 2026-10-30, so timing is unknown; Ferrite 1.7.0 is the current release). Assessment: an unstructured FEM Poisson or Maxwell solve is what geometry-heavy electrostatic problems need (electrodes, structures), not what LWFA needs (structured box, moving window, GPU throughput, charge-conserving deposition matched to the Yee stagger); GPU assembly in Ferrite could not be verified. Value: a second mesh backend that proves the slot and the description/implementation split, for geometry-heavy electrostatic problems, which no planned module covers (A9: the electromagnetic module is the only one); no role in the LWFA module.
- DG through Trixi.jl: the inspected copy (0.11.1; 0.17.18 registered) carries a 1D Maxwell equation type; DG-PIC is an established method family, but charge conservation and the particle–mesh coupling on DG meshes are a research topic of their own, and Trixi's GPU support (TrixiCUDA, CUDA-only, unregistered; a multi-GPU prototype) is not at the level of the KA path. Value: a third mesh backend and the precedent of `semidiscretize` turning a mesh solver into an `ODEProblem` right-hand side; not for the first module.
- Fast multipole as a mesh-free alternative for the long-range slot: FastMultipole.jl 2.3.0 (BYU FLOW Lab; Laplace kernel, CPU-parallel expansions, CUDA only for the direct interactions, ForwardDiff- and ReverseDiff-compatible per its README) and ExaFMMt.jl 0.1.2 (wrapper). Not needed for LWFA; relevant only if a pairwise or gravity module wants long-range sums without a mesh.
- TrixiParticles.jl 0.5.3 (SPH with KA kernels on NVIDIA, AMD and Apple per the March 2026 poster and the JuliaCon 2026 talk) and PointNeighbors.jl 0.6.7 (`GridNeighborhoodSearch` with `FullGridCellList` marked GPU-compatible, GPU support still "work in progress"): precedents for a KA particle framework whose coupled particle systems form one `Semidiscretization`, and a candidate neighbour search for the pairwise and P³M slot (§0.3) to compare with the engine's own cell sorting. SPH itself is a different physics (fluids whose particles carry the state) and enters only if a module wants it.

### 0.6 Time integration on Reactant: the harness ties the ladder together

`sciml-reuse.md` §1 wraps the hand-written step in a `DiscreteProblem` with `FunctionMap` (OrdinaryDiffEq) or `SimpleFunctionMap` (SimpleDiffEq), and the reduced models of the ladder are ODE problems. Two facts make this harness the natural Reactant entry point: SimpleDiffEq already runs under Reactant (prior work, to be reused), and OrdinaryDiffEq PR #4436 "Share ordinary solver paths with Reactant" (a draft; what it changes and its status are in the landscape table, `landscape-and-requirements.md` §3) makes explicit solves inside Reactant compilation run the ordinary `solve!` loop, with untraceable options throwing before tracing. So on the Reactant path the PIC step runs under `SimpleFunctionMap` or a `@trace` loop now, and under the shared OrdinaryDiffEq loop once #4436 lands (whether it covers `FunctionMap` is part of the B9 spike). The level-0 and level-1 reduced models run on Reactant through the same solvers, so the whole ladder, not only the PIC core, sits on the compiler path. Diagnostics then live outside the traced solve, as saved states or as reductions inside the step; Molly's lesson that loggers are ignored by AD applies.

### 0.7 Engine core: contracts

The contracts are written from the code of the spike WP-010 (`reports/spike-electrostatic-1d.md`) as A0 asks; each states what it guarantees and the test that proves it, and changes only together with its code and test. Everything else about the engine is still open and listed as a proposal at the end of this section. Code: `lib/ParticleMeshCore/src`; tests and tolerances: `lib/ParticleMeshCore/test`. `N = 1` and `N = 2` are implemented (WP-018: periodic, one device; contracts 11 and 13 are `N = 1` only); the code is written generic in `N` where that costs nothing, but only `N = 1` and `N = 2` are claimed and tested. Every `N = 1` signature, return type and bit is the one before the port (T-260: digests of every entry point recorded before it, at 1 and 4 threads).

What the engine is. The engine holds the physics-free pieces: species, the grid and its guards, the transfers between particles and mesh, the sort, loading and mesh operators. It names no physics: no exported name contains Gauss, Poisson or Electrostatic and the engine defines no physics submodule (T-171). The engine owns no `System`, `State` or `step!`: a physics module composes its own step from engine pieces, in its own order (an electromagnetic step with charge-conserving deposition needs the old positions and the Yee half-steps, which the engine must not fix), and that composition, with the separation of problem description and numerics of A10 (§0.5), is owned by the electromagnetic module (WP-014). §1 and §2 list kernels of the whole stack, not of the engine: Yee, Boris, the filter, absorbing layers, the antenna and the moving window belong to the electromagnetic and LWFA modules. The electrostatic cases run through the electromagnetic module with no transverse fields (A9: there is no electrostatic module; T-213 to T-215).

The contracts:

1. **Grid.** `PeriodicGrid(n, dx, g)` for `N = 1` and `PeriodicGrid(n::NTuple{N}, dx::NTuple{N}, g)`, a plain immutable `PeriodicGrid{N,T}`: `n_d` interior cells of size `dx_d` (c/ω₀) per axis and one guard width `g` per side for every axis; cell `i` of axis `d` covers `[(i-1)dx_d, i·dx_d)`; a field is a column-major array of size `n .+ 2g` with interior index `i ↦ i + g` per axis, allocated by `field(backend, T, grid)`; `n_d ≥ 2g` (the tuple constructor checks it per axis). Cells linearize column-major, axis 1 fastest: `linear_cell(c, n)` and its inverse `cartesian_cell(L, n)`. The `N = 1` accessors (`ncells`, `cellsize`, `length`, `interior`, `interior_view`) return scalars and one range as before; for `N = 2` `ncells`, `cellsize` and `interior` return one entry per axis (T-261). Periodicity is topology and belongs to the engine; what happens at a bounded edge belongs to the module.
2. **Species.** `Species(backend, T, capacity; q, m, N = 1, extras = NamedTuple())`: a structure of arrays at fixed capacity (§0.4 rule 1: no `push!` or `resize!`): `cell::NTuple{N}` of `Int32` arrays and `offset::NTuple{N}` of `T` arrays in `[0, 1)` per resolved axis, so Float32 positions keep their precision far from the origin; `u::NTuple{3}`, which holds whatever the module says (velocities in the reference, momenta in the electromagnetic module); the weight `w`; `status` (`0x01` alive, `0x00` free); `count`, a one-element device array written by kernels (sort, load) and never read inside a step; per-species `q` and `m`; and `extras`, a `NamedTuple` of module-declared arrays at capacity, each of its own element type, declared by element type (`extras = (old_cell = Int32, old_offset = T)`) and allocated on the species' backend.
3. **Position advance.** `advance(cell, δ, Δ, n)`: the offset stays in `[0, 1)`, including the case where `δ + Δ - floor(δ + Δ)` rounds up to one; the cell wraps; exact for dyadic `Δ`, through the seam and for `Dual` (T-138). With `NTuple{N}` arguments it applies per axis, so a diagonal move through a corner wraps both axes (T-261). `floor` of a `Dual` offset gives a plain integer, so the cell carries no partials and the derivative is that of the continuous trajectory. On periodic axes this wrap is the single-device implementation of the particle exchange; `exchange_particles!` is the later multi-device entry point that replaces it.
4. **Shapes.** `Shape{P}` with the order as type-level configuration (`Linear`, `Quadratic`; cubic later), staggers `Node()` and `Center()`; `shape_weights(shape, stagger, δ)` gives the first node and `P + 1` weights summing to one (T-130); `guard_width(Shape{P}) = P`. For `N` axes one `Shape{P}` applies to every axis and a stagger is an `NTuple{N,Stagger}` (mixed pairs such as `(Center(), Node())` included): `shape_weights` returns the per-axis `(f, w)`, `stencil_reach` the per-axis reach, and the weight of a node is the tensor product `w_1[k_1]·w_2[k_2]` multiplied in axis order, which `tensor_weights` lists column-major; it sums to one and equals the outer product of the 1D weights bitwise (T-262). Each order's natural stagger (order 1 at nodes, order 2 at centres) has a stencil independent of `δ`; the other two pairs need `floor` and a wider `stencil_reach`, and are tested too.
5. **Guards.** `fill_guards!(a, grid)` copies the periodic images of the interior into the guards; `fold_guards!(a, grid)` adds the guards into the interior cells they alias and zeroes them; they are adjoints over the full arrays (T-133). For `N = 2` they run axis by axis with the corners included: fill does axis 1 on the interior rows of axis 2, then axis 2 on every column; fold is its transpose, axis 2 first, then axis 1 on the interior rows (T-263). The guard convention is "deposit into guards, then fold": both deposition modes write the contributions that cross the seam into the guards, and `fold_guards!` moves them into the interior.
6. **Gather.** `gather!(out, a, species, shape, stagger, grid)`: the field (guards filled) at every alive particle; it reproduces constant and linear fields (T-131), and for `N = 2` constant and bilinear fields `a + b·x + c·y + d·x·y`, with the per-particle `gather_at` inferred to return `T` (T-264).
7. **Deposition.** `deposit!(mode, ρ, species, shape, stagger, grid, ws; quantity = ChargeWeight())` adds `quantity(species, i)` of every alive particle into `ρ` (with guards). `quantity` is a module-supplied isbits device callable, `ChargeWeight()` (q·w) by default; the default path is bitwise the spike's q·w deposition (T-174). The deposited total equals the sum of the quantity (T-134, T-174), deposition is the adjoint of `gather!` with the same weighting, fill and fold included (T-132, T-175), and `Dual` weights give exact partials (T-140, T-175). Two modes: `Reference()` needs `sort_by_cell!` since the last particle move, and one work item per node (guards included) adds the contributions of the cells in its stencil in increasing cell order, within a cell in slot order, with no scratch; it is bitwise reproducible across reruns and thread counts for one element type on one backend (A4, T-174, T-177). `Fast()` adds with atomics. The two agree per node within `C·eps(T)·Σ|contributions|` (T-135, T-174). For `N = 2` the same holds with the tensor-product weights (T-265): a node adds the contributions of its stencil's cells in increasing column-major linear index, within a cell in slot order, which is the A4 bitwise contract for `N = 2` (T-266, at 1 and 4 threads and three launch shapes, with particles crossing both seams and the corner). The kernel visits those cells as the `CartesianIndices` of the per-axis cell ranges: measured on prototypes before the port (`reports/wp-018-engine-2d.md`), it ties explicit nested per-axis loops within the run-to-run spread, beats a recursive `Val{N}` tuple loop nest by 15 to 25 %, and is generic in `N`. The tensor product makes the 2D Reference deposition cost 2.4 to 3.1 times the 1D Reference deposition per particle at the natural staggers and 4.0 to 4.8 times at the others (geometric means at 4 and 1 threads), where the floor of the offset widens the stencil; at the natural staggers it is cheaper than the 2D `Fast()` path on the CPU backend, at the others about twice as expensive (Float32 and Float64, 1 and 4 threads, CPU only). A 2D load constant along one axis reduces to the 1D deposit and gather to roundoff (T-269).
8. **Accumulation trait.** `accumulation(T)` is `Atomic()` for Float32 and Float64 and `Sorted()` for every other type; `effective_mode(Fast(), T)` is `Reference()` for a `Sorted()` type, so `Dual` and compensated types take the sorted path with no type-specific code in the engine (A8), for every `N`.
9. **Sort.** `sort_by_cell!(species, grid, ws)` sorts by the key `cell·capacity + slot` (for `N > 1` the column-major linear cell, an `Int64` key whose overflow is checked), free slots after every cell; the keys are unique, so the permutation does not depend on the algorithm, the backend or the thread count (T-136, T-173). The one permutation is applied to every core array and to every extra (T-173; `ws.perm[i]` is the slot that slot `i` held before), and the per-cell segment bounds (per linear cell) and the alive count are written (T-266). `Workspace(species, grid)` holds the scratch, allocated once: keys, permutation, the AcceleratedKernels sort workspace, one permutation buffer per core element type (`Int32`, `T`, `UInt8`), and one more per further element type among the extras; `Int32` and `T` extras reuse the core buffers and an empty tuple costs nothing (33 B per particle for Float32 and 37 B for Float64 with or without a two-array extras tuple of `Int32` and `T`, `scripts/em1d/flux_timing.jl`; in 2D the same per particle plus 8 B per linear cell for the segment bounds, with or without those extras, `scripts/engine2d/timing.jl`).
10. **Loading.** `load_quiet!(species, grid, density, p, ppc; vdrift, vth, seed, stream)`: `ppc` particles per cell on the lattice `(k - 1/2)/ppc`, velocity components from Box–Muller over Philox4x32-10 (known answers, T-139) keyed by `(seed, stream)` with the counter `(cell, 0, 0, k << 16)`, so a seed means the same thing on every backend (A4); weights `density(x, p)/ppc`, so parameters enter through the weights only (A3). For `N = 2`, `ppc::NTuple{2}` on the per-axis product lattice `δ_d = (k_d − 1/2)/ppc_d`, the in-cell index `k` linear with axis 1 fastest (`prod(ppc) < 2^16`, checked), the counter `(cell₁, cell₂, 0, k << 16)`, the slots in linear-cell order, and weights `density(x::NTuple{2}, p)/prod(ppc)`; positions do not depend on `p` (T-267).
11. **Periodic prefix sum.** `cumsum_periodic!(out, a, grid)`: the zero-mean periodic antiderivative of the field `a` on the interior, written into the field `out` with its guards filled: `(out[j] - out[j-1])/dx = a[j] - mean(a)` and `Σ_j out[j] = 0`, both to `C·eps(T)` times `n·max|a|` (times `dx` for the mean) (T-172). The association order is part of the contract and is fixed by the operator, not by the launch configuration or the backend: tiles of the package constant `SCAN_TILE = 1024` elements, a serial left-to-right sweep from zero inside each tile, the tile totals combined by a serial exclusive scan in tile order and each tile's offset added once to its elements (none to the first tile); the two means are sums over the same tiles in the same order. The result is bitwise equal to a plain serial implementation of that order, on one tile and on several, and bitwise across reruns, thread counts and launch shapes (T-172, T-177). It runs as one work item on every backend, CUDA included (T-192), so CPU and CUDA results differ only by the backends' own arithmetic (measured in T-197); the module calls it once, for the field at t = 0, and a parallel kernel of the same order waits for a profile that shows it. The engine does not name the equation; with that initial field the module keeps Gauss's law to roundoff after every step (T-212).
12. **Launch keyword.** Every engine launch takes `workgroupsize = nothing`, where `nothing` is the backend's KernelAbstractions default: `sort_by_cell!`, `deposit!`, `gather!`, `fill_guards!`, `fold_guards!`, `load_quiet!`, `cumsum_periodic!`, `deposit_flux!`, `inverse_laplacian_periodic!`, `gradient_periodic!` and the table kernel of `SpectralWorkspace`, and every later engine launch, the `N = 2` methods included. It selects only the launch shape; in `Reference()` mode it does not change the bits (A4; T-177, T-113, T-266, T-312 on the CPU, T-192 and T-196 on CUDA). An integer size on a two-dimensional launch applies to axis 1. The AcceleratedKernels sort inside `sort_by_cell!` launches as its workspace plan says, and the one-work-item scan ignores the keyword (its guard fill takes it).

13. **Charge-conserving flux.** `deposit_flux!(mode, Jx, Jy, Jz, species, shape, stagger, grid, ws; dt, quantity_y, quantity_z)` adds the current of one step (Esirkepov's scheme, which for `N = 1` reduces to a prefix sum of the change of the shape weights over the stencil) into three fields with ρ's layout. The old position comes from the extras `old_cell::Int32` and `old_offset::T`, which the module stores before its push and the sort carries. `Jx[j]` is the face half a cell to the right of ρ's node `j`, at ρ's index `j`: for ρ at `Node()` it is `Center()` index `j`, for ρ at `Center()` it is `Node()` index `j + 1`, and the continuity equation of T-110 pins the offset; per particle it is `-(q·w·Δx/dt)` times the running sum, in increasing node order, of `W_new - W_old`. `Jy` and `Jz` sit on ρ's nodes and are the module's quantities (`q·w·u_y/γ` for a current) times the weights averaged over the old and new position. With ρ from `deposit!` with the same shape and stagger, discrete continuity `(ρ_new[j] - ρ_old[j])/dt + (Jx[j] - Jx[j-1])/Δx = 0` holds to `C·eps(T)·max|ρ|/dt`, in both modes, for orders 1 and 2, every stagger and the required element types, with a sort between storing the old position and depositing (T-110), and the residual of each step does not grow over a drift (T-111). `Σ Jy` is `Σ quantity_y` and `Σ Jx` is `Σ q·w·Δ/dt` (T-112); Reference and Fast agree per face within `C·eps(T)·Σ|contributions|`, and Reference is bitwise across reruns, thread counts and launch shapes (T-113); the flux is linear in the weights, with exact `Dual` partials (T-114); a particle at rest deposits exactly zero `Jx` (T-115). Through a cell crossing the flux of order 2 is C¹ in the displacement (AD against `fd_scan`, T-116); order 1 is C⁰, with a kink where the end point crosses a node of its stagger. Preconditions: a move of less than one cell per step, the seam included (larger moves are not detected); `n ≥ 3`; at least `flux_guard_width(shape, stagger)` guard cells, one more than `guard_width` except for order 2 at `Center()`, because the old and new stencils together reach one node further (checked). `Reference()` needs `sort_by_cell!` after the move; the guard convention is `deposit!`'s (fold each field). The engine knows no Maxwell equation: Gauss's law for a field is the electromagnetic module's test (WP-014). `N = 1` now; the N-D formula comes with the first N-generic package.
14. **Periodic spectral inverse of the discrete Laplacian.** `SpectralWorkspace(backend, T, grid)` holds the scratch, allocated once: per axis the twiddle tables `cos` and `sin` of `2πm/n_d`, written by a kernel from `sincospi(T(2m′)/T(n_d))` with `m′ = min(m, n_d − m)` (the angle reduced exactly in integers, the tables exactly conjugate-symmetric), and `N` pairs of real and imaginary spectrum arrays of `prod(n)` entries. `inverse_laplacian_periodic!(φ, s, grid, ws)` writes into the field `φ`, guards filled, the zero-mean periodic solution of `L φ = s − mean(s)` with `L = Σ_d D⁻_d D⁺_d`, `D⁺_d` the forward and `D⁻_d` the backward difference; the guards of `s` are not read and `φ` may be `s`. `gradient_periodic!(G::NTuple{N}, φ, grid)` writes `G_d[j] = (φ[j + e_d] − φ[j])/Δ_d` at index `j`, the face half a cell to the right of node `j` (`Center()` on axis `d`, `Node()` on the others: at every `N` the Yee layout of Ex and Ey of the electromagnetic module's `field_layout` below, at `N = 1` also the layout of `cumsum_periodic!`'s output), guards filled, the guards of `φ` not read. Then `Σ_d D⁻_d G_d = s − mean(s)` at every node and `mean(φ) = 0`, to `C·eps(T)` times `(Σ_d n_d)·(max|s| + ‖L‖·max|φ|)` with `‖L‖ = Σ_d 4/Δ_d²` (times `Σ_d n_d·max|φ|` for the mean; T-310: the residual grows like the square root of `Σ_d n_d` from 16 × 12 to 256 × 192 and from 64 to 4096 cells, so the ratio falls with the size); an oblique mode on a non-square grid with `Δx ≠ Δy` reproduces the closed form `φ = −s/K²` with the Yee-consistent symbol `K² = Σ_d (2 sin(π k_d/n_d)/Δ_d)²`, and its gradient (T-311); at `N = 1`, `G_1` agrees with `cumsum_periodic!` (T-313). Sign: `+L φ = s − mean(s)` and `G = +∇φ`, so a module that wants `div E = s` takes `E = G`; the module names the equation (Gauss's law with `s = ρ`), not the engine. Method: the DFT per axis (axis 1 from the real interior, then axis 2), every mode `k ≠ 0` divided by `−K²` with the sine's argument reduced exactly to `min(k_d, n_d − k_d)/n_d`, the `k = 0` mode set to zero, the inverse DFTs in reverse axis order, the real part divided by `prod(n)`. The association order is part of the contract and fixed by the operator: one work item per output entry of a transform (a mode or node of the transformed axis and one index of every other axis) sums the `n_d` terms of its line serially in increasing order from zero, the twiddle index `k·j mod n_d` advanced in integers; so the result is bitwise across reruns, thread counts and launch shapes, a reused workspace and an in-place solve included (T-312, at 1 and 4 threads and three launch shapes, even and odd sizes, `N = 1` and `N = 2`). The solve is linear in `s`, so `Dual` partials are the solve of the partials of `s`, and the primal agrees with the Float32 run, both to `C·eps(T)` (T-314; the primal measured bitwise, which is recorded and not asserted, A4). It is O(`prod(n)·Σ_d n_d`) per solve and meant for the field at t = 0 (times, and what a production solver needs, in `reports/wp-021-periodic-solve-2d.md`); allocation per call does not grow with the grid (T-315); a workspace of another size or element type, a grid without guards and a gradient written into `φ` are refused (T-316). No new dependency: FFTW takes only Float32 and Float64, and Krylov solvers give no fixed order, so neither is on the Reference path. `N = 1` and `N = 2`.

The electromagnetic module's step (WP-014, `lib/ParticleMeshElectromagnetic`). The module, not the engine, owns the step and its order, composed from the contracts above. Its field layout is a module-declared rule in N, `field_layout(Val(N))`, a `NamedTuple` of engine staggers with ρ on the primal nodes (`Node()` on every axis, for every shape order): component c of E and of J sits at `Center()` along axis c and `Node()` along every other resolved axis, component c of B at `Node()` along axis c and `Center()` along the others, and a component of a collapsed axis (c > N) at `Node()` (E, J) or `Center()` (B) on every axis. At N = 1 it is `FIELD_LAYOUT`: ρ, Ey, Ez, Bx, Jy, Jz at `Node()` and Ex, By, Bz, Jx half a cell to the right at `Center()`, which is `deposit_flux!`'s layout with ρ at `Node()`; at N = 2 Ex and Jx at (Center, Node), Ey, Jy and Bx at (Node, Center), Ez at (Node, Node), By at (Center, Node), Bz at (Center, Center), the layout the Smilei and PIConGPU sources state (`reports/wp-022-yee-nd.md`); `em_fields` allocates it on any `PeriodicGrid{N}`. The guards are `flux_guard_width(shape, Node())`. The momenta `u` are `γv`. `initialize!` loads each species from the problem description (`load_quiet!`, velocities converted to momenta), solves Ex from the deposited charge with `cumsum_periodic!` (as Smilei solves at t = 0) and moves the momenta half a step back with the pusher. `step!` then runs: diagnostics of Eⁿ, Bⁿ; per species, store the old cell and offset as extras, push the momentum in Eⁿ, Bⁿ gathered at xⁿ and move the particle; sort where the mode needs it; zero, `deposit_flux!` and fold Jx, Jy, Jz; deposit the kinetic energy for the diagnostics; the mesh solve (Yee: B half step, E full step with J, B half step). `solve_fields!(::Yee, f, grid::PeriodicGrid{N}, dt)` writes the curl once over the resolved axes (forward differences from `Node()` to `Center()`, backward from `Center()` to `Node()`, a collapsed axis dropped by dispatch), one work item per interior node, and fills the guards of every component it changes (Bx is dynamic from N = 2); N = 1 and N = 2 are claimed. At N = 1 it is the earlier 1D solver bit for bit (a digest of the 1D vacuum and case runs, before and after, at 1 and 4 threads). Against the exact discrete theory of the scheme: an oblique eigenmode in each polarization follows sin(ωΔt/2)/Δt = √(Σ_d sin²(k_dΔ_d/2)/Δ_d²) to roundoff (T-320), the phase-velocity error against c falls as Δ² (T-321), ∇·B is kept and ∇·E changes by −Δt·∇·J (T-322), the energy Σ E² + Σ Bⁿ⁻¹ᐟ²·Bⁿ⁺¹ᐟ² is kept in vacuum and changes by the work term −Δt Σ J·(Eⁿ + Eⁿ⁺¹) (T-323), a y-invariant 2D run is the 1D run bit for bit and the axis exchange maps runs onto runs (T-324), bitwise across reruns, threads and launch shapes (T-327), linear for `Dual` (T-328), guards periodic and allocation flat in the grid (T-329). Its stability limit belongs to the solver: `courant_limit(::Yee, grid)` = 1/√(Σ_d 1/Δ_d²) (exactly Δx at N = 1), beyond which the highest mode grows by (S + √(S² − 1))² per step (T-325); `check_courant(solver, grid, dt)` throws an `ArgumentError` naming it, and the state constructor calls it (T-326), which with |v| < c also keeps every particle within one cell per axis per step, as `deposit_flux!` needs. `solve_fields!` itself does not check Δt. Gauss's law then follows from continuity and holds to roundoff after every step without a re-solve (T-212); the electrostatic edge cases keep Ey, Ez, Bx, By, Bz at +0.0 bit for bit (T-213). Problem description and numerics are separate types (A10): an `EMProblem` (box, species, parameters in A1 units, built from a case file) names no kernel, and an `EMNumerics` chooses the shape, the deposition mode, the pusher (`Boris <: Pusher`, so WP-015 adds pushers without touching the step) and the mesh solver (`Yee`) by type.

Element types (A8). The required matrix is Float32, Float64 and `Dual{Float32,3}` (A8's required set), all through the same kernels, and every test above runs it where the test applies. Double32 is a later trial package, not part of the matrix. No `DiffCache`: state and workspaces are built in the execution element type, which is enough for ForwardDiff. Bitwise reproducibility holds per element type and backend (A4); the value part of a `Dual` run is not the primal run bit for bit (the loader's weights differ by an ulp in a few particles), so comparisons across element types are measured tolerances.

Acceptance (A7). Exact identities are held to `C·eps(T)` scaled by the problem size, with `C` measured and proposed in `lib/ParticleMeshCore/test/tolerances.toml`, which the test suite reads and whose measured ratios it prints after every run. Allocation per call of every engine operation does not grow with the particle count or the grid size, with or without extras (T-144 at N = 1, T-268 at N = 2, T-315 for the periodic solve: measured at two sizes after warm-up, not as zero bytes); the module holds its whole step to the same rule (T-220). The finite-difference floor of a gradient check is defined operationally by the test helper `fd_scan(f, x0, hs; seed, ad)` (`lib/ParticleMeshCore/test/helpers.jl`): central difference quotients over at least five steps; the floor is the spread (maximum minus minimum) of three neighbouring quotients, minimised over the scan and taken relative to the AD value; the check is `rel ≤ C·floor` at the minimising step, with `C` proposed in `tolerances.toml` (T-219 measures 0.176 and asserts 1). A7's three conditions are part of the definition: Float64 even where production is Float32 (`fd_scan` throws otherwise), the Reference mode on both sides (every evaluation is `f(x, Reference(), seed)`) and common random numbers (one seed for every evaluation); computing the AD value with the same `f`, mode and seed is the caller's obligation (T-176).

Reactant (§0.4, A9). Every kernel above keeps rules 1 to 6; three are the likeliest to need work once Reactant is unparked: the Reference deposition loops over data-dependent segment bounds, `cumsum_periodic!` is a one-work-item loop, and the sort is AcceleratedKernels'. The periodic solve of contract 14 runs one loop of static length per work item with a gather from its twiddle tables at an integer index. None is tested under Reactant yet.

Proposals, not yet tested in code: a static grid separate from a small dynamic grid state (the moving window's hook, B1); one element type per array so that accumulators may differ from particles (B5); `fill`/`fold`/`exchange` as the three communication points that later carry the multi-device exchange; `Wakefields` as its own package in `lib/`, layered on the electromagnetic module (which is one, WP-014), and the user layer `ParticleMesh` holding unit conversion (A1) and case setup (A5).

## 1. Layering

The rule: the hot loop is plain numeric kernels over typed arrays; everything symbolic generates code that plugs into those kernels, never the other way around. That is the EDM pattern applied to a grid code.

```
L4  Optimization / campaigns     Optimization.jl, BO baseline, run manifests, cloud (EDM backends)
L3  Symbolic front-end (opt.)    MTK particle models → force kernels; MOL staggered groups → Maxwell update;
                                 LaserTypes.jl / Symbolics expressions → laser & density kernels; parameter identities
L2  Differentiation              tangent-bundle layout (value + P tangents), Dual-number push, per-component atomics;
                                 Enzyme forward/reverse on kernels; Reactant path: same KA kernels traced, raised, sharded (smoke test once Reactant is unparked, A9)
L1  Parallel layout              PeriodicGrid{N} with guard cells, slab/block decomposition, halo + particle exchange,
                                 moving window as a global shift; single device → multi-device node → MPI
L0  Core numerics                SoA fields and particles, KernelAbstractions kernels: gather, push, deposit,
                                 Yee E/B, filter, inject, absorb; generic in N (§0.8); physics modules plug in via §0.1
```

The layers describe the whole stack, engine and physics modules together; which pieces are the engine's is fixed in §0.7. L0 and L1 have no symbolic dependency and are the first deliverable. L3 is an optional package extension that reuses EDM. The engine/module split of §0.1 cuts across the layers: the engine is the L0–L2 machinery, a physics module is a set of L0 kernels (and, through L3, their generators) plugged into the interaction interfaces.

## 2. Core numerics (L0)

This section lists the kernels of the whole stack, not of the engine: the engine holds the physics-free transfers, the sort, guards, loading and mesh operators (§0.7), and Yee, Boris, the filter, absorbing layers, injection and the window belong to the electromagnetic and LWFA modules.

Data layout
- Fields: one `AbstractArray{T,N}` per component, its stagger an `NTuple{N,Stagger}` (§0.8), guard cells sized by the shape-function order (§0.7). The components are the module's: the electromagnetic module declares Ex, Ey, Ez, Bx, By, Bz, Jx, Jy, Jz and optionally ρ with Yee staggers. In 2D3V all field and momentum components exist and vary only along the two resolved axes, as in Smilei and PIConGPU; the grid is `PeriodicGrid{2}` and the collapsed axis is not stored (§0.7), which keeps one kernel source for N = 1, 2, 3.
- Particles (per species): SoA buffers with `cell::Int32` per resolved axis plus an in-cell offset `T` in [0, 1) per resolved axis, momentum `T × 3`, weight, alive mask, optional tag (§0.7). The cell+offset split is what keeps FP32 usable over a long moving window (PIConGPU layout); FP32 is required on the 4080 SUPER (FP64 at 1/64 rate), FP64 is available on rented datacenter GPUs (MI300X, NVIDIA data-center cards). `T` is a type parameter throughout and is chosen at the user level; nothing assumes Float64 or Float32. The same kernels run every element type of A8's required matrix (§0.7); the deposition kernel selects its accumulation path by a trait on `T` (atomics for primitive types, the sorted segmented reduction for every other type (§0.7)). See `docs/goals/A8-element-type.md`.
- Fixed-capacity buffers with periodic compaction and cell sorting (supercells). Sorting also enables a deposition variant without atomics (segmented reduction), which matters for the Reactant path and for deterministic bitwise reproducibility.

Kernels (KernelAbstractions, `foreachindex` style as in EDM)
- `gather!`: tensor-product shape functions (order 2 or 3; order 1 only for tests, its kinks hurt gradients), per-component staggering.
- `push_particles!` (the module's hook, §0.7): Boris by default in the electromagnetic module; the force term is a pluggable callable so that L3 can substitute an MTK-generated force (Lorentz + Landau–Lifshitz, later quantum corrections). For non-Lorentz forces a generic RK/implicit per-particle step replaces Boris.
- `deposit_flux!` (engine, §0.7 contract 13), which the electromagnetic module calls for the current: Esirkepov, N = 1 now, N = 2 in its own package (§0.8 item 2); atomics only on primitive components, the sorted path otherwise (§0.7).
- `yee_E!`, `yee_B!`: curl stencils over guard cells; Lehe or PSATD solver later for numerical Cherenkov.
- `filter!` (binomial), `absorb!` (PML or simple damping layers), `inject!` (plasma at the window front, laser antenna at a plane), `window_shift!`.
- Time loop: the module's `step!` is the unit (the engine owns none, §0.7). Tests drive it with `run!`, a plain loop; runs drive it through the `DiscreteProblem`/`FunctionMap` harness of §0.6, which supplies saved states and `remake`. No ODE integrator acts inside the step: the harness only calls it at fixed steps (§0.7).

Validation targets: Landau damping, two-stream, Weibel (JAX-in-Cell set), 1D wake against the analytic nonlinear wake, 2D LWFA against Smilei and PIConGPU (containerized setups exist), energy and charge conservation.

## 3. Parallel layout (L1): 2D now, multi-GPU 3D later

- The multi-device grid carries a global extent, a local block, and guard regions; the 2D slice stays single-device (§0.8). Single-device runs use the same code with a no-op exchange.
- Decomposition: start with a 1D slab decomposition along the propagation axis. It matches the moving window (ranks form a ring; the window advance is a whole-cell shift where the front rank injects and the back rank drops), keeps halo exchange one-dimensional, and already covers one node of eight GPUs. 3D block decomposition and load balancing (particles concentrate in the bubble and bunch) come after.
- Exchange primitive: `fill_guards!(fields, grid, gstate)`, its adjoint `fold_guards!(fields, grid, gstate)` after deposition, and `exchange_particles!(species, grid)` as the only communication points (§0.7); on a single device they implement periodic axes and nothing else. Implementations in order: none (single device); device-to-device copies between devices of one node driven by one Julia task per device (EDM's sharding pattern, generalized from "split the electrons" to "split the domain"); CUDA-aware MPI.jl for multi-node. ImplicitGlobalGrid.jl is a candidate for the structured-grid halo part (GPU-aware MPI, CUDA and AMDGPU); particle migration is ours.
- Vendor portability stays free through KernelAbstractions plus GPUDiagnostics.jl, so the MI300X cloud route remains open.
- Prototyping without a multi-GPU box: run the decomposition on the KA CPU backend with MPI on a many-core CPU, or several ranks on one GPU, before renting a multi-GPU instance.

### On skipping quasi-3D

RZ with azimuthal modes is a separate numerics path (cylindrical Maxwell, mode-decomposed deposition) that does not advance the multi-GPU 3D goal. The cost reducer that keeps Cartesian geometry and the same kernels is the laser envelope (ponderomotive guiding center) model: it removes the λ₀ resolution along the propagation axis, 10 to 30 times fewer cells, and the ponderomotive force is smoother than the resolved laser oscillation, which is good for gradients. Suggested path: 2D full PIC → 2D envelope → 3D envelope on one node → 3D full PIC for production checks. Validity (a₀ up to a few, pulse length much larger than λ₀) covers the LWFA regime of interest.

## 4. Differentiation (L2)

### Forward mode with about 3 parameters (phase 1)

- Tangent-bundle layout rather than `CuArray{Dual}`: every field and particle array exists as a value array plus `P` tangent arrays. Inside `push_particles!` and `gather!` the thread loads value and tangents into a local `ForwardDiff.Dual{Tag,T,P}`, does the arithmetic, and stores the components back. `deposit_flux!` (§0.7 item 13) adds value and each tangent with separate primitive atomics, since atomics on `Dual` structs are not available. `P = 0` recovers the primal code with no overhead.
- Cost: memory and FLOPs scale as `P + 1`. A 2D run at 2048 × 512 cells, 16 particles per cell, FP32, P = 3 needs roughly 2 GB for particles, which fits the 4080.
- Which parameters are active is a setup-time decision (a₀, w₀ or τ, n₀, focus position, ramp length). Through L3 these are symbolic parameter identities, so "active parameter" is a tag on the MTK parameter and the tangent seeding is generated, not hand-written.
- Noise and non-smoothness (cell crossings, injection events) are discussed with the objective; the layout above is neutral to that discussion.

### Where Enzyme helps

- Enzyme forward mode with `BatchDuplicated` shadows over the same SoA layout could replace the hand-rolled Dual load/store with less code and possibly better register use. Worth a phase 2 comparison on `push_particles!`.
- Reverse mode becomes necessary when the parameter count grows (pulse shaping with 10 to 100 spectral coefficients, a spline- or network-parameterized density profile). Plan: `Enzyme.autodiff(Reverse, step!, ...)` per time step with a checkpointing schedule over the loop (store full state every k steps, recompute in between), custom rules for `deposit_flux!` if Enzyme does not handle the atomics (its adjoint is a gather, easy to write by hand). Open Enzyme-on-CUDA bugs as of Oct 2026 (`cis` in kernels, `fill!`, tape types) are tracked in the landscape notes; none is a blocker for forward mode.
- Enzyme on MTK-generated scalar force functions is well-trodden; the L3 symbolic force is not a risk for AD.

### Where Reactant helps

- Reactant compiles whole Julia array programs to XLA with Enzyme-MLIR for both AD modes, supports `@trace` loops with automatic checkpointing, and has multi-device sharding. A PIC written as array operations (sort, segmented reduction for deposition, gather by indexing, stencil broadcasts) would get fusion, sharding and reverse mode in one go. That is the JAX-in-Cell route and the most direct bridge to the symbolic layer, because generated array code (including MOL's fused staggered update) can be traced.
- Risks as of Oct 2026: gather/scatter under reverse mode has open correctness and performance regressions, compile times, and control-flow restrictions. Since A9 Reactant is a declared long-term target, not an experiment, and the mechanism is verified (§0.2): the KA kernels are traced through `ReactantBackend` and raised, so no array rewrite is needed; the deposition kernel stays available in both atomic and sort-based forms so the raised path is a backend, not a rewrite; AD inside Reactant works only on raised kernels, so forward mode on that path is Enzyme-MLIR forward over the raised program, while the Dual layout above stays the native-path implementation behind the `jvp` interface (§0.4, rule 8). Whether `Dual`-valued locals inside a kernel survive raising is untested and part of the B9 spike. The first Reactant target is the 1D3V level, where parity with JAX-in-Cell is a day's work; Reactant on CPU needs no GPU, so a smoke test belongs in CI as soon as Reactant is unparked (A9: parked until it supports GPUCompiler 2 and KernelAbstractions 0.10).

## 5. Symbolic front-end (L3): the door kept open

The principle this layer serves is stated in §0.5: the symbolic layer is how problem description and numerical implementation are kept apart, which is why it stays in the design even though hand-written kernels are the production path.

What EDM already gives, and how it maps onto PIC:

| EDM today | ParticleMesh use |
|---|---|
| `ChargedParticle(external_field, radiation_model)` composed from `ParticleDynamics`, `EMFieldDynamics`, forces | same components with a `GridField` input in place of `external_field`: E and B at the particle are kernel inputs; `mtkcompile` + `build_function` yield a device-callable force or RHS |
| Landau–Lifshitz generated for any field | radiation reaction in the pusher for free; quantum-corrected LL later as one more component |
| LaserTypes.jl fields, unit systems | laser antenna/initial fields and density profiles as symbolic expressions compiled to kernels; SI/natural units handled once |
| parameters via SymbolicIndexingInterface, tunables | the active-parameter set for the tangent layer |
| run manifests, campaigns, dashboard | unchanged |

On the grid side, MOL's `staggered_groups` with `scalarize_single_element_regions = false` produces resolution-independent fused-broadcast Yee updates that run on the GPU (measured in `landscape-and-requirements.md` §4.1). It can be an alternative Maxwell backend behind the same `yee_E!`/`yee_B!` interface once (a) a constructor from the `System` avoids the `DAEProblem` residual build (§4.1 there; a small MOL PR), (b) current sources and guard-cell exchange are added. ModelingToolkit #5139 would extend this to arbitrary array models; worth tracking, not worth waiting for.

What this buys: composable physics models, units, documentation value, and symbolic parameter identities for AD; what it costs: nothing on the hot loop, since the generated code is scalar per particle or fused per slice.

## 6. Hardware mapping

| Stage | Machine | Precision | Notes |
|---|---|---|---|
| L0/L1 development, 1D and 2D | local 4080, KA CPU backend for tests | FP32 (FP64 for CPU reference) | 16 GB limits 2D with P = 3 to ~10⁷ particles |

## 7. Suggested order of work
