You implement exactly one work package. The package is one or two sentences: what to build and how to show it works. Everything below that is yours to decide. Read the goals it lists, the code it builds on and, when you touch the engine, `docs/plan/architecture-draft.md` §0; then write a short plan (what you build, which checks show it is right) and change it as the code teaches you. Trust the code over any document that predates it.

The deliverable is working code plus evidence. Hold each new piece to a closed form, an exact discrete identity or a conservation law near roundoff (A7), and compare with theory or another code where the package names one, with figures from `scripts/` (F3). Each test checks what its name says and fails when the thing it guards breaks: say in the PR how you saw it fail. Add the Julia packages you need yourself (F2). Keep every rule of `CLAUDE.md`'s "Rules that are never relaxed".

Run the CPU test matrix before opening the PR. In the same PR, set the package's `status` to `done` when its sentences hold, otherwise to `active`, with what is left in the PR description; rewrite its sentences only if they turned out wrong, and say why. If a decision blocks you, write `questions/<id>.md` with your assumption and continue. After opening the PR, wait for its checks before you end (`gh pr checks <n> --watch --fail-fast`, in a background command): read a failure with `gh run view <run id> --log-failed` (strip the colour codes with `sed 's/\x1b\[[0-9;]*m//g'`), push the fix, and wait again; the `Julia pre` job may fail, which the PR notes. The PR description gives the plan as it ended, what you built, the evidence (measured numbers, not adjectives) and every assumption, briefly. Work you found and left goes into a `follow-up` issue, a defect outside your package into a `bug` issue.
