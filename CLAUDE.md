# ParticleMesh.jl: instructions for every Claude session

ParticleMesh.jl is a differentiable particle–mesh simulation engine in Julia with pluggable physics modules. First module: electromagnetic particle-in-cell for laser-wakefield acceleration. Long term: a showcase and stress test for Julia and Reactant compiler technology. This file is the contract for every agent session, local or cloud.

## Orientation (read in this order)

1. `docs/goals/`: the owner's aims (A0) and binding decisions (A1 to A10). Short; read all of it.
2. The work package you were given, in `trace/wp/`, and the documents it points to.
3. `docs/plan/architecture-draft.md` section 0 when you touch the engine: the engine/module split, the interfaces, the Reactant rules.

Everything else in `docs/plan/` is background (`docs/plan/README.md` says which is which); read it when the package or a question needs it.

## Rules that are never relaxed

- This repository is public. Never commit hostnames, ssh aliases, IP addresses, machine user names, tokens, or the names of private packages or products. Describe hardware by GPU or CPU model ("RTX 4080 SUPER", "MI300X").
- Julia 1.13 is the target (`julia +1.13` with juliaup). CI runs 1.13; the next pre-release is allowed to fail.
- The engine works in normalized units with the laser frequency as reference: time in 1/ω₀, length in c/ω₀, fields in m_e c ω₀/e, density in units of the critical density. Unit conversion lives only in the user layer.
- The element type `T` is generic. No float literals in kernels (`zero(T)`, `T(π)`, `eps(T)`). Float32, Float64 and ForwardDiff duals must pass the CPU test matrix.
- Kernels are KernelAbstractions kernels. No scalar indexing outside kernels. Allocate with `similar` or `KernelAbstractions.allocate`. Static shapes: fixed-capacity particle buffers with an alive mask and a count; no `push!` or `resize!` inside a step; no host-side branching on device data.
- Deposition exists in two variants, atomics and sort plus segmented reduction, and the tests check that they agree.
- Engine code never references a specific physics; physics modules plug in through the interaction interfaces. The engine must not depend on ModelingToolkit, MethodOfLines, Molly or Checkpointing.jl.
- Parameters enter through particle weights and sources, never through particle positions.
- Reference mode is deterministic: counter-based random numbers, sort-based deposition, bitwise reproducibility tested.
- Reactant is parked until it supports GPUCompiler 2 and KernelAbstractions 0.10 (A9): add no Reactant dependency, but keep every kernel within the Reactant rules of `docs/plan/architecture-draft.md` §0.4. Once unparked, the Reactant CPU smoke test is part of CI. If it fails, fix the kernel; do not remove the test. If the failure is in Reactant itself (the native CPU test of the same kernel passes), open an `upstream` issue with a minimal reproducer, mark the test `@test_broken` with the issue number, and park that Reactant feature until upstream is fixed (A9).
- Never fabricate citations, expected values or benchmark numbers; mark anything unverified as such.
- No comments in `Project.toml` files; explain compat choices in the commit message.
- Dependencies (F2): add what your package needs with `Pkg.add` in your own worktree, with a compat entry for every direct dependency of the root and `lib/` packages, re-resolve `scripts/Manifest.toml` when the root manifest changes, and list the change in the PR description. If `Manifest.toml` conflicts after a rebase, take the base branch's version, re-add your packages (or `Pkg.resolve()`), run the tests and push. If you can see other sessions on the machine, tell them what you are adding; do not wait for an answer.
- Plots are made with CairoMakie from `scripts/`, never from package code; every plot is saved as PNG next to a JSON sidecar with the scalar values it shows.

## Layout

A Pkg workspace: the umbrella package at the root, with `test/`, `docs/`, `benchmark/` and the `lib/` subpackages as workspace members sharing the committed root `Manifest.toml` (`lib/` packages are reached through `[sources]` with relative paths, so every worktree is self-contained). `scripts/` is its own environment outside the workspace, with a committed manifest, for the user code that produces results: benchmark cases, validation and cross-code runs, campaigns, figures. `reports/` Markdown reports with their figures; `docs/goals/` the owner's aims and decisions; `docs/plan/` the design derived from them; `trace/` work packages, the trace checker's specification and digests; `questions/`; `.claude/agents/` roles; `.claude/workflows/` saved workflows.

## Working here

- Work in a worktree: `git fetch`, then EnterWorktree (worktrees live under `.claude/worktrees/`, ignored by git, branched from `origin/main`). Instantiate with `julia +1.13 --project -e 'using Pkg; Pkg.instantiate()'`, run the CPU tests, open a PR. Every worktree pays one precompilation against the shared depot; keep dependency lists short.
- Tests: `julia +1.13 --project -e 'using Pkg; Pkg.test()'`; for a subpackage, `--project=lib/<Name>`. One `Pkg.instantiate()` at the root covers the whole workspace; `scripts/` instantiates separately. GPU tests run only with `PM_TEST_GPU=1` and through `scripts/gpu-lock.sh`, which serializes GPU use between agents. Never run GPU work from two worktrees at once. A sandboxed session has no GPU; where the machine provides a `gpu-runner` session (see that machine's own CLAUDE.md), request the run from it instead of trying CUDA locally.
- Test names carry an id and what they verify, goals or work packages: `@testset "T-031 Esirkepov charge conservation [A2, WP-004]"`. Ids are unique; pick one past the highest in use. `julia +1.13 --project=scripts scripts/trace/build.jl --check` checks the links (`trace/README.md`).
- Do not ask blocking questions. Write the question and the assumption you proceeded on to `questions/<id>.md`, say so in the PR description, and continue.
- Permissions in unattended sessions. Factory and cloud sessions run in auto mode: a classifier reviews each action against your task, inside the sandbox and the deny rules, which stay hard limits. Pipes, chains and variables are fine there. A denied action is skipped and the session goes on: say in the PR description what was denied and what you did instead, and never rephrase a command to get past a denial. Sessions in GitHub Actions (the review and package-manager workflows) run under exact allow lists instead: a call runs only if every part of it matches a rule, and shell variables, `$(...)`, backticks, loops and `VAR=value` prefixes are refused because they cannot be checked before they run. Everywhere, text for GitHub (PR bodies, reviews, comments) is written to a file first and posted with `--body-file`.
- Stage files by name (`git add <path>`), never `git add -A` or `git add .`: inside the sandbox, `git status` also lists the sandbox's placeholder mounts (`.bashrc`, `.gitconfig`, `.gitmodules`, `.claude/skills`, ...) as untracked entries; they are not files and must never be staged.
- Goals: `docs/goals/` is the owner's and states each aim and decision as it stands; git is its history. Derive from it, never contradict it. If one is wrong or blocks you, write `questions/<id>.md`; you may also propose the edit in a PR that says why (tier 2). Everything below the goals is yours to keep consistent: requirements, interfaces and plans in `docs/plan/`, work packages in `trace/wp/`. When you change a work package against a goal, refresh its `[checked]` entries (`build.jl --refresh WP-nnn`). Never write "decided on <date>" and never keep superseded text next to the new one.
- Pull requests (F4): merging is GitHub's job, not yours: never merge a pull request yourself, by any route. `main` takes squash merges only, through pull requests with green required checks and one approving review. The approval for tier 0 and tier 1 comes from the automated review (`.github/workflows/review.yml`: a code lens on every PR and a numerics lens when the diff touches code, the goals or `docs/plan/architecture-draft.md`, briefs in `.claude/agents/code-reviewer.md` and `numerics-reviewer.md`, read from the base branch); tier 2 is every path listed in `.github/CODEOWNERS`. A factory-app PR on a tier-2 path also needs the owner's approval. A PR authored by the owner's account, which is every cloud session's, merges on the gate alone, because GitHub does not ask an author to approve their own change. So an unattended session (a scheduled task, a workflow run, any session nobody is steering) opens a PR that touches a tier-2 path as a draft and leaves it there for the owner, and never marks it ready or enables auto-merge on it. The gate labels every reviewed tier-2 PR `tier-2`, and the digest lists them. After opening a PR, enable auto-merge once, `gh pr merge --auto --squash`, and move on: GitHub merges when the requirements are met and deletes the branch. Answer a "changes requested" review by pushing; approvals are dismissed on push and re-earned by the next review run. The PR description becomes the squash commit message, so it carries the attribution and the ids of the goals and work packages it touches. Do not open a PR only to address minor review findings: the gate collects them in a `follow-up` issue, the hourly janitor (`.claude/agents/janitor.md`, `.github/workflows/janitor.yml`) fixes the mechanical ones, and the planner picks up the rest. Keep a PR in draft while it should not be reviewed. A change to a file under `.github/workflows/` goes in its own commit and the PR description says so. A cloud session, which acts as the owner's account, pushes it like any other commit; local factory sessions cannot (the factory app has no Workflows permission), so they leave that commit for the owner to push. Workflow files are a code-owner path either way, so the tier-2 rules above apply. Tiers are defined in `docs/plan/factory-and-observability.md`.
- Identities on GitHub: local factory sessions act as the app `particlemesh-factory[bot]`; cloud sessions act as the owner's account and mark their posts with the Claude Code attribution line. A comment from the owner's account without that line is the owner speaking; everything else is another agent.
- Cloud sessions reach GitHub through a proxy that rejects GraphQL and passes REST. So `gh pr ...`, `gh issue ...` and `gh label list` fail there with a 403, while REST commands such as `gh label create` work (`gh api` would too, but `.claude/settings.json` denies it). Use the GitHub MCP tools for pull requests, issues and comments: creating issues and comments, marking a PR ready for review and enabling auto-merge (`enable_pr_auto_merge`, squash) all work through them.
- Anything you post on GitHub (PR descriptions, issues, comments) states that it was written by Claude Code and names the model id where the harness allows. Commits carry the attribution trailer the harness provides. Replace your home directory by `~` in any path you post.
- Before benchmark numbers or scientific claims leave the repository (a README table, a paper, a talk), they get an independent review by a fresh reviewer session.
- Runs produce the standard plot set with scalar sidecars; each run writes a manifest next to its outputs with the commit and the hashes of its inputs (F3). Reports are Markdown in `reports/`, with the header `reports/README.md` describes and the figures committed next to them.

## Issues

- Open and comment on issues in this repository freely, one problem per issue. Search the open issues first and comment on a match instead of opening a duplicate. Label it for routing: `upstream` (a suspected bug in a dependency or in Julia), `factory` (the setup or the process: sandbox denials, depots, the GPU runner, tooling, a rule in this file that cannot be followed, goals that contradict each other; say what you tried, the exact error, the workaround, the time lost), `bug` (a defect in this repository outside your task), `follow-up` (work you found and left). Then continue.
- Never post in another repository, and never edit, delete or transfer an issue. Close an issue only through a merged PR whose description says `Fixes #<n>`; humans and triage sessions close the rest. Issues are public: the rules for this repository's content apply to them, and the CI scan does not see them.
- A suspected upstream bug goes to a fresh `upstream-reporter` subagent (`.claude/agents/upstream-reporter.md`): it reduces the problem to a minimal working example that does not depend on this repository, confirms it in a clean temporary environment and posts it as an `upstream` issue here. Meanwhile work around it, except for Reactant failures, which are parked instead (A9). Humans and sessions outside the factory file it upstream.
- Never retry a denied action outside the sandbox or look for another way in; open a `factory` issue.

## Background jobs and waiting

- Never wait for another process with a loop over `pgrep -f "<pattern>"`: the waiting shell's own command line contains the pattern, so the loop waits on itself (this has stalled a queued benchmark for twenty minutes before). Chain dependent work in one command (`cmd1; cmd2`, or `&` and `wait`), or wait on the exact PID (`while kill -0 <pid> 2>/dev/null; do sleep 10; done`). To wait for a condition, such as a line in a log file, use the Monitor tool; a session under exact allow lists (see "Working here") can wait no other way. If a pattern is unavoidable, write it so it cannot match itself: `pgrep -f '[b]ench.jl'`.
- A GPU job requested from the runner is finished when its log file ends with a line starting `# gpu-run finished:`; wait for that line, not for a process.

## Julia notes

- Find a package's location with `julia +1.13 --startup=no --project -e "using X; Base.pkgdir(X)"`; package versions are in the `Manifest.toml` of the environment you are in (a manifest may be versioned per Julia release, `Manifest-v1.13.toml`).
- Test and docs environments use `[sources]` to reach the packages in this repository; do not `Pkg.develop` over them.
- Prefer `foreachindex`-style KernelAbstractions kernels; `Atomix` for atomics; `Adapt` for structs crossing to the device.
