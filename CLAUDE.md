# ParticleMesh.jl: instructions for every Claude session

ParticleMesh.jl is a differentiable particle–mesh simulation engine in Julia with pluggable physics modules. First module: electromagnetic particle-in-cell for laser-wakefield acceleration. Long term: a showcase and stress test for Julia and Reactant compiler technology. This file is the contract for every agent session, local or cloud.

## Orientation (read in this order)

1. `docs/goals/`: the owner's aims (A0) and binding decisions (A1 to A10). Short; read all of it.
2. The work package you were given, in `trace/wp/`, and the documents it points to.
3. `docs/plan/architecture-draft.md` section 0 when you touch the engine: the engine/module split, the interfaces, the Reactant rules.

Everything else in `docs/plan/` is background (`docs/plan/README.md` says which is which); read it when the package or a question needs it.

## Rules that are never relaxed

A checklist for every change and every review; where a rule names an id, its full text is there.

- This repository is public: no hostnames, ssh aliases, IP addresses, machine user names, tokens, or names of private packages or products, and hardware is named by GPU or CPU model ("RTX 4080 SUPER", "MI300X") (A6).
- Julia 1.13 is the target (`julia +1.13` with juliaup), with the next pre-release allowed to fail in CI (A6).
- The engine works in normalized units with the laser frequency ω₀ as reference, and unit conversion lives only in the user layer (A1).
- The element type `T` is generic, with no float literals in kernels (`zero(T)`, `T(π)`, `eps(T)`) and the CPU test matrix Float32, Float64 and `Dual{Float32,3}` (A8; `docs/plan/architecture-draft.md` §0.7).
- Kernels are KernelAbstractions kernels within the Reactant rules: static shapes (fixed-capacity buffers, an alive mask and a count, no `push!` or `resize!` inside a step), no scalar indexing outside kernels, allocation through `similar` or `KernelAbstractions.allocate`, no host-side branching on device data (§0.4).
- Deposition exists as atomics and as sort plus segmented reduction, and the tests check that they agree (A4, §0.4 rule 3).
- Engine code never references a specific physics (physics modules plug in through the interaction interfaces) and depends on none of the packages F2 forbids (A9, F2).
- Parameters enter through particle weights and sources, never through particle positions (A3).
- Reference mode is deterministic: counter-based random numbers, sort-based deposition, bitwise reproducibility per element type and backend, tested (A4).
- Reactant is parked: no Reactant dependency, every kernel within §0.4, Reactant failures handled as A9 says (A9).
- Never fabricate citations, expected values or benchmark numbers; mark anything unverified as such.
- No comments in `Project.toml` files; explain compat choices in the commit message.
- A compat entry for every direct dependency of the root and `lib/` packages, with both manifests re-resolved together (F2; procedure under "Working here").
- Plots are made with CairoMakie from `scripts/`, never from package code, each a PNG next to a JSON sidecar; every run writes a manifest next to its outputs, and reports follow `reports/README.md` (F3).

## Layout

A Pkg workspace (F1): the umbrella package at the root, with `test/`, `docs/`, `benchmark/` and the `lib/` subpackages as members sharing the committed root `Manifest.toml` (`lib/` packages are reached through `[sources]` with relative paths, so every worktree is self-contained); `scripts/` its own environment with a committed manifest, for the user code that produces results: benchmark cases, validation and cross-code runs, campaigns, figures (F3). `reports/` Markdown reports with their figures; `docs/goals/` the owner's aims and decisions; `docs/plan/` the design derived from them; `trace/` work packages, the trace checker's specification and digests; `questions/`; `.claude/agents/` roles; `.claude/workflows/` saved workflows.

## Working here

- Work in a worktree (under `.claude/worktrees/`, ignored by git, branched from `origin/main`). Sessions start inside their worktree and never call EnterWorktree. The factory launchers, and the machine's wrapper for interactive sessions, run `git fetch` and `git worktree add --no-track -b worktree-<name> .claude/worktrees/<name> origin/main`, then start the session there. A launched session's sandbox sees only its own worktree, not the main checkout or the other worktrees. A session that finds itself in the main checkout, for example one dispatched from the agent view, runs that same command itself, `cd`s into the new worktree and works only there. It never writes in the main checkout. EnterWorktree is not used because it switches on a git isolation guard that refuses ordinary commands (#53); this is a workaround for a Claude Code issue, dropped when the guard is fixed. Instantiate with `julia +1.13 --project -e 'using Pkg; Pkg.instantiate()'`, run the CPU tests, open a PR. Every worktree pays one precompilation against the shared depot; keep dependency lists short.
- Tests: `julia +1.13 --project -e 'using Pkg; Pkg.test()'`; for a subpackage, `--project=lib/<Name>`. One `Pkg.instantiate()` at the root covers the whole workspace; `scripts/` instantiates separately. GPU tests run only with `PM_TEST_GPU=1` and through `scripts/gpu-lock.sh`, which serializes GPU use between agents. Never run GPU work from two worktrees at once. A sandboxed session has no GPU; where the machine provides a `gpu-runner` session (see that machine's own CLAUDE.md), request the run from it instead of trying CUDA locally.
- Test names carry an id and what they verify, goals or work packages: `@testset "T-110 Esirkepov charge conservation [A2, WP-009]"`. Ids are unique; pick one past the highest in use. `julia +1.13 --project=scripts scripts/trace/build.jl --check` checks the links (`trace/README.md`).
- Do not ask blocking questions. Write the question and the assumption you proceeded on to `questions/<id>.md`, say so in the PR description, and continue.
- Permissions in unattended sessions. Factory sessions (except the GPU runner, which keeps narrow allow rules) and cloud sessions run in auto mode: a classifier reviews each action against your task, inside the sandbox and the deny rules, which stay hard limits. Pipes, chains and variables are fine there. A denied action is skipped and the session goes on: say in the PR description what was denied and what you did instead, and never rephrase a command to get past a denial. Sessions in GitHub Actions (the review, package-manager and janitor workflows) run under exact allow lists instead: a call runs only if every part of it matches a rule, and shell variables, `$(...)`, backticks, loops and `VAR=value` prefixes are refused because they cannot be checked before they run. Everywhere, text for GitHub (PR bodies, reviews, comments) is written to a file first and posted with `--body-file`.
- Stage files by name (`git add <path>`), never `git add -A` or `git add .`: inside the sandbox, `git status` also lists the sandbox's placeholder mounts (`.bashrc`, `.gitconfig`, `.gitmodules`, `.claude/skills`, ...) as untracked entries; they are not files and must never be staged.
- Goals: `docs/goals/` is the owner's, and its rules are in `docs/goals/README.md`. Derive from it, never contradict it. If one is wrong or blocks you, write `questions/<id>.md`; you may also propose the edit in a PR that says why (tier 2). Everything below the goals is yours to keep consistent: requirements, interfaces and plans in `docs/plan/`, work packages in `trace/wp/`. When you change a work package against a goal, refresh its `[checked]` entries (`build.jl --refresh WP-nnn`). Never write "decided on <date>".
- One home per fact (`docs/goals/README.md`): decisions in the goals A0 to A10; factory settings in F1 to F4 (`docs/plan/factory-and-observability.md` §5); how sessions operate in this file; design in `docs/plan/`; trace rules in `trace/README.md`; tier-2 paths in `.github/CODEOWNERS`; role briefs in `.claude/agents/`; one package's tasks in its work package. Elsewhere, cite the fact by id in one clause instead of copying it; a reviewer reports a new full copy as a minor finding.
- Current state, history in git (`docs/goals/README.md`): documents and work packages say what holds now. Delete what is done, answered, superseded or withdrawn instead of marking it, and put what is worth keeping (why, what replaced it, where the outcome lives) into the commit message, where `git log -S` finds it. On `main` that message is the PR description, since `main` takes squash merges, so the record goes there. Do not write status words such as "Closed", "(now)", "superseded" or "was" next to text that should simply go.
- Dependencies (F2): add what your package needs with `Pkg.add` in your own worktree, add the compat entries, re-resolve `scripts/Manifest.toml` when the root manifest changes, and list the change in the PR description. If `Manifest.toml` conflicts after a rebase, take the base branch's version, re-add your packages (or `Pkg.resolve()`), run the tests and push. If you can see other sessions on the machine, tell them what you are adding; do not wait for an answer.
- Pull requests: the merge policy and the review gate are F4; tiers are defined in `docs/plan/factory-and-observability.md` §3e, and tier 2 is every path listed in `.github/CODEOWNERS`. Merging is GitHub's job, not yours: never merge a pull request yourself, by any route. After opening a PR, enable auto-merge once, `gh pr merge --auto --squash`, and move on. An unattended session (a scheduled task, a workflow run, any session nobody is steering) opens a PR that touches a tier-2 path as a draft and leaves it there for the owner, and never marks it ready or enables auto-merge on it, because a PR from the owner's account merges on the gate alone (F4). Keep a PR in draft while it should not be reviewed. Answer a "changes requested" review by pushing; approvals are dismissed on push and re-earned by the next review run. The PR description becomes the squash commit message, so it carries the attribution and the ids of the goals and work packages it touches. Do not open a PR only to address minor review findings (F4). A change to a file under `.github/workflows/` goes in its own commit and the PR description says so; a cloud session pushes it like any other commit, while a local factory session cannot (the factory app has no Workflows permission) and leaves that commit for the owner to push. Workflow files are a code-owner path either way, so the tier-2 rules above apply.
- Identities on GitHub: local factory sessions act as the app `particlemesh-factory[bot]`; cloud sessions act as the owner's account and mark their posts with the Claude Code attribution line. A comment from the owner's account without that line is the owner speaking; everything else is another agent.
- Cloud sessions reach GitHub through a proxy that rejects GraphQL and passes REST. So `gh pr ...`, `gh issue ...` and `gh label list` fail there with a 403, while REST commands such as `gh label create` work (`gh api` would too, but `.claude/settings.json` denies it). Use the GitHub MCP tools for pull requests, issues and comments: creating issues and comments, marking a PR ready for review and enabling auto-merge (`enable_pr_auto_merge`, squash) all work through them.
- Anything you post on GitHub (PR descriptions, issues, comments) states that it was written by Claude Code and names the model id where the harness allows. Commits carry the attribution trailer the harness provides. Replace your home directory by `~` in any path you post.
- Before benchmark numbers or scientific claims leave the repository (a README table, a paper, a talk), they get an independent review by a fresh reviewer session.

## Issues

- Open and comment on issues in this repository freely, one problem per issue. Search the open issues first and comment on a match instead of opening a duplicate. Label it for routing: `upstream` (a suspected bug in a dependency or in Julia), `factory` (the setup or the process: sandbox denials, depots, the GPU runner, tooling, a rule in this file that cannot be followed, goals that contradict each other; say what you tried, the exact error, the workaround, the time lost), `bug` (a defect in this repository outside your task), `follow-up` (work you found and left). Then continue.
- Never post in another repository, and never edit, delete or transfer an issue. Close an issue only through a merged PR whose description says `Fixes #<n>`; humans and triage sessions close the rest. Issues are public: the rules for this repository's content apply to them, and the CI scan does not see them.
- A suspected upstream bug goes to a fresh `upstream-reporter` subagent (`.claude/agents/upstream-reporter.md`): it reduces the problem to a minimal working example that does not depend on this repository, confirms it in a clean temporary environment and posts it as an `upstream` issue here. Meanwhile work around it, except for Reactant failures, which are parked instead (A9). Humans and sessions outside the factory file it upstream.
- Never retry a denied action outside the sandbox or look for another way in; open a `factory` issue.

## Background jobs and waiting

- Never wait for another process with a loop over `pgrep -f "<pattern>"`: the waiting shell's own command line contains the pattern, so the loop waits on itself (this has stalled a queued benchmark for twenty minutes before). Chain dependent work in one command (`cmd1; cmd2`, or `&` and `wait`), or wait on the exact PID (`while kill -0 <pid> 2>/dev/null; do sleep 10; done`). To wait for a condition, such as a line in a log file, use the Monitor tool; a session under exact allow lists (see "Working here") can wait no other way. If a pattern is unavoidable, write it so it cannot match itself: `pgrep -f '[b]ench.jl'`.
- A GPU job requested from the runner is finished when its log file ends with a line starting `# gpu-run finished:`; wait for that line, not for a process.

## Julia notes

- Find a package's location with `julia +1.13 --startup=no --project -e "using X; Base.pkgdir(X)"`; package versions are in the `Manifest.toml` of the environment you are in (a manifest may be versioned per Julia release, `Manifest-v1.13.toml`).
- Test and docs environments use `[sources]` to reach the packages in this repository; do not `Pkg.develop` over them.
- Prefer `foreachindex`-style KernelAbstractions kernels; `Atomix` for atomics; `Adapt` for structs crossing to the device.
