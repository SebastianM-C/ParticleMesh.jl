# ParticleMesh.jl: instructions for every Claude session

ParticleMesh.jl is a differentiable particle–mesh simulation engine in Julia with pluggable physics modules. First module: electromagnetic particle-in-cell for laser-wakefield acceleration. Long term: a showcase and stress test for Julia and Reactant compiler technology. This file is the contract for every agent session.

## Orientation (read in this order)

1. `docs/goals/`: the owner's aims (A0) and binding decisions (A1 to A10). Short; read all of it.
2. The work package you were given, in `trace/wp/`, and the documents it points to.
3. `docs/plan/architecture-draft.md` section 0 when you touch the engine: the engine/module split, the interfaces, the Reactant rules.

Everything else in `docs/plan/` is background (`docs/plan/README.md` says which is which); read it when the package or a question needs it.

## Rules that are never relaxed

A checklist for every change and every review; where a rule names an id, its full text is there.

- This repository is public: no hostnames, ssh aliases, IP addresses, machine user names, tokens, or names of private packages or products, and hardware is named by GPU or CPU model ("RTX 4080 SUPER", "MI300X") (A6).
- Julia 1.13 is the target (`julia +1.13` with juliaup), with the next pre-release allowed to fail in CI (A6).
- The engine works in normalized units with the laser frequency ω₀ as reference, and unit conversion lives only in the user layer (A1).
- The element type `T` is generic, with no float literals in kernels (`zero(T)`, `T(π)`, `eps(T)`) and the CPU test matrix Float32, Float64 and `Dual{Float32,3}` (A8; `docs/plan/architecture-draft.md` §0.7).
- Kernels are KernelAbstractions kernels within the Reactant rules: static shapes (fixed-capacity buffers, an alive mask and a count, no `push!` or `resize!` inside a step), no scalar indexing outside kernels, allocation through `similar` or `KernelAbstractions.allocate`, no host-side branching on device data (§0.4).
- Deposition exists as atomics and as sort plus segmented reduction, and the tests check that they agree (A4, §0.4 rule 3).
- Engine code never references a specific physics (physics modules plug in through the interaction interfaces) and depends on none of the packages F2 forbids (A9, F2).
- Parameters enter through particle weights and sources, never through particle positions (A3).
- Reference mode is deterministic: counter-based random numbers, sort-based deposition, bitwise reproducibility per element type and backend, tested (A4).
- Reactant is parked: no Reactant dependency, every kernel within §0.4, Reactant failures handled as A9 says (A9).
- Never fabricate citations, expected values or benchmark numbers; mark anything unverified as such.
- No comments in `Project.toml` files; explain compat choices in the commit message.
- A compat entry for every direct dependency of the root and `lib/` packages, with both manifests re-resolved together (F2; procedure under "Working here").
- Plots are made with CairoMakie from `scripts/`, never from package code, each a PNG next to a JSON sidecar; every run writes a manifest next to its outputs, a run's bulk data goes to its run branch rather than into `reports/`, and reports follow `reports/README.md` (F3).

## Layout

A Pkg workspace (F1): the umbrella package at the root, with `test/`, `docs/`, `benchmark/` and the `lib/` subpackages as members sharing the committed root `Manifest.toml` (`lib/` packages are reached through `[sources]` with relative paths, so every clone is self-contained); `scripts/` its own environment with a committed manifest, for the user code that produces results: benchmark cases, validation and cross-code runs, campaigns, figures (F3). `reports/` Markdown reports with their figures; `docs/goals/` the owner's aims and decisions; `docs/plan/` the design derived from them; `trace/` work packages and the trace checker's specification; `questions/`; `.claude/agents/` roles.

## Working here

- Where sessions run. Threads of the owner's Claude project do the work: cloud sessions with a fresh clone and a branch of their own (`claude/project-thread-*`), without a GPU, acting on GitHub as the owner's account. GitHub Actions runs CI, the review gate and the weekly package manager. GPU work runs on the owner's GPU machines, driven from a thread ("GPU machines" below), or on rented GPUs.
- Start: instantiate with `julia +1.13 --project -e 'using Pkg; Pkg.instantiate(workspace = true)'`, run the CPU tests, open a PR. Every fresh clone pays one precompilation; keep dependency lists short. A `cd` does not reliably carry over to the next shell call, so a git or Pkg command names its directory itself: `cd <absolute path> && ...` in the same call, or `--project=<path>`.
- Tests: `julia +1.13 --project -e 'using Pkg; Pkg.test()'`; for a subpackage, `--project=lib/<Name>`, and `PM_TEST_GROUP=<n>` runs one of the groups in its `test/groups.toml`, as CI's parallel jobs do (a new test file goes into a group there, or the suite refuses to run). One `Pkg.instantiate(workspace = true)` at the root covers the whole workspace (without `workspace = true` it installs only what the root project reaches, #517); `scripts/` instantiates separately. A cloud container has 4 cores and about 15 GB: run at most two test groups at once (a third was killed for memory), and set `JULIA_NUM_THREADS=1` for the one-thread allocation checks, which the container's default of 4 skips.
- Long CPU runs (Smilei on the CPU, full-size ParticleMesh CPU runs, anything past about 20 minutes) can go to the rented CPU box (16 cores, AMD EPYC 9655) through git: `scripts/cpu-box.sh submit <tag> <request.toml>` pushes a branch `runs/<tag>`; wait for `scripts/cpu-box.sh status <tag>` to print the result (Monitor with an until-loop), then `scripts/cpu-box.sh fetch <tag>` puts it into `scripts/runs/box-<tag>/`; the branch stays as the record of the run. Request branches are public and permanent, so the script refuses large or leak-matching inputs. The format and the limits are in the script's header. It also runs test suites (a julia step with `--project=lib/<Name>` and `Pkg.test()`): ParticleMeshCore's and the scripts' tests, but not ParticleMeshElectromagnetic's while #339 is open, so that suite runs in the cloud container or in CI. For a campaign longer than a session should wait, submit it as a batch with a `CONTINUE.md` on your branch and end: a fresh cloud session continues when the last result is back (the script's header). Cloud sessions can push `runs/` branches; the GitHub proxy does not restrict which branches a push updates. The box is a spot instance and can disappear: a request with no result after its timeout plus an hour may also be run in the session (the late box result then lands in its own directory), and the PR says so. Name the box in reports by its CPU model.
- Run data (F3): `scripts/rundata/run-data.sh publish <tag> <dirs>` pushes a run's outputs to `runs/<tag>` and writes the `published.toml` that the report commits next to the run's manifest; `run-data.sh fetch <published.toml>` (or `<tag>`) brings them back and checks their hashes. A clone need not download the run branches: `git config --add remote.origin.fetch '^refs/heads/runs/*'` (fetching one by name still works).
- Test names carry an id and what they verify, goals or work packages: `@testset "T-110 Esirkepov charge conservation [A2, WP-009]"`. Ids are unique; a package's tests take the next free block of ten (T-360 to T-369 after T-35x), so parallel packages do not collide. `julia +1.13 --project=scripts scripts/trace/build.jl --check` checks the links (`trace/README.md`).
- Do not block on a question. Ask it in your thread, or write it to `questions/<id>.md`; either way state the assumption you proceed on, say so in the PR description, and continue.
- Permissions. Cloud threads run in auto mode: a classifier reviews each action against your task, inside the deny rules of `.claude/settings.json`, which stay hard limits. A denied action is skipped and the session goes on: say in the PR description what was denied and what you did instead, and never rephrase a command to get past a denial. Sessions in GitHub Actions (the review and package-manager workflows) run under exact allow lists instead: a call runs only if every part of it matches a rule, and shell variables, `$(...)`, backticks, loops and `VAR=value` prefixes are refused because they cannot be checked before they run. Text that `gh` posts on GitHub (PR bodies, reviews, comments) is written to a file first and posted with `--body-file`.
- Stage files by name (`git add <path>`), never `git add -A` or `git add .`.
- Check the repository's state twice. When you start: the open pull requests and the `claude/*` branches for your work package or the files you will touch; if another session already has it, take something else or say in the PR how the two fit. Before you open the PR: `git fetch` and `git log HEAD..origin/main --stat`; when something merged since your branch point touches your files, or adds what your tests enumerate (keys, cases, test ids), take `main` into your branch, run your tests and fix what breaks. Each PR is reviewed alone, so this is the only check that two PRs fit together (on 2026-11-03 #286 and #282 each passed and together turned `main` red).
- Taking `main` into your branch: merge it (`git merge origin/main`) and never rebase a pushed branch, since run manifests cite its commit ids. GitHub's squash merge combines the branch with `main`, so you need the merge only to test against `main` or to pick up a workflow fix: an open pull request keeps running the workflow file of its last merge commit, and only a new commit on the branch changes that, not a re-run.
- Goals: `docs/goals/` is the owner's, and its rules are in `docs/goals/README.md`. Derive from it, never contradict it. If one is wrong or blocks you, write `questions/<id>.md`; you may also propose the edit in a PR that says why (tier 2). Everything below the goals is yours to keep consistent: requirements, interfaces and plans in `docs/plan/`, work packages in `trace/wp/`. A work package is one or two sentences (`trace/README.md`): write new ones that way, and plan the details yourself when you implement one. Never write "decided on <date>".
- One home per fact (`docs/goals/README.md`): decisions in the goals A0 to A10; factory settings in F1 to F4 (`docs/plan/factory-and-observability.md` §5); how sessions operate in this file; design in `docs/plan/`; trace rules in `trace/README.md`; tier-2 paths in `.github/CODEOWNERS`; role briefs in `.claude/agents/`; one package's tasks in its work package. Elsewhere, cite the fact by id in one clause instead of copying it.
- Current state, history in git (`docs/goals/README.md`): documents and work packages say what holds now. Delete what is done, answered, superseded or withdrawn instead of marking it, and put what is worth keeping (why, what replaced it, where the outcome lives) into the commit message, where `git log -S` finds it. On `main` that message is the PR description, since `main` takes squash merges, so the record goes there. Do not write status words such as "Closed", "(now)", "superseded" or "was" next to text that should simply go.
- Dependencies (F2): add what your package needs with `Pkg.add`, add the compat entries, re-resolve `scripts/Manifest.toml` when the root manifest changes, and list the change in the PR description. If `Manifest.toml` conflicts when you take `main`, take `main`'s version, re-add your packages (or `Pkg.resolve()`), run the tests and push.
- Pull requests: the merge policy and the review gate are F4; tiers are defined in `docs/plan/factory-and-observability.md` §3e, and tier 2 is every path listed in `.github/CODEOWNERS`. Merging is GitHub's job, not yours: never merge a pull request yourself, by any route. After opening a PR, enable auto-merge once (squash) and move on. An unattended session (a scheduled task, a workflow run, any session nobody is steering) opens a PR that touches a tier-2 path as a draft and leaves it there for the owner, and never marks it ready or enables auto-merge on it, because a PR from the owner's account merges on the gate alone (F4). Workflow files are such a path. Keep a PR in draft while it should not be reviewed. Never assign the owner to a PR or request his review: threads act as his account, and GitHub does not let an author review their own pull request. Answer a "changes requested" review by pushing; approvals are dismissed on push and re-earned by the next review run. The PR description becomes the squash commit message, so it carries the attribution and the ids of the goals and work packages it touches. Do not open a PR only to address minor review findings (F4).
- Identities on GitHub: cloud threads act as the owner's account and mark their posts with the Claude Code attribution line; the package manager's Actions session acts as the app `particlemesh-factory[bot]`, and the review gate as `github-actions[bot]`. A comment from the owner's account without that line is the owner speaking; everything else is another agent.
- Cloud sessions reach GitHub through a proxy that rejects GraphQL and passes REST. So `gh pr ...`, `gh issue ...` and `gh label list` fail there with a 403, while REST commands such as `gh label create` work (`gh api` would too, but `.claude/settings.json` denies it). Use the GitHub MCP tools for pull requests, issues and comments: creating issues and comments, marking a PR ready for review and enabling auto-merge (`enable_pr_auto_merge`, squash) all work through them.
- Anything you post on GitHub (PR descriptions, issues, comments) states that it was written by Claude Code and names the model id where the harness allows. Commits carry the attribution trailer the harness provides. Replace your home directory by `~` in any path you post.
- Before benchmark numbers or scientific claims leave the repository (a README table, a paper, a talk), they get an independent review by a fresh reviewer session.

## GPU machines

The owner's GPU machines (a PC with an RTX 4080 SUPER, a workstation with an RTX 5090) are reached from a thread through Remote Control. How to reach each one is in the project's memory, never in this repository (A6).

- One GPU job at a time per machine. Every GPU job, a test suite included, takes the machine's GPU lock: through `scripts/gpu-lock.sh`, or through the machine's queue where it has one. A command waits at most 4 hours for the lock; if the lock is not free by then it does not run and the script exits 75 with "lock wait exceeded", which is a reason to resubmit, not a test failure. A queued job is finished when its log ends with a line starting `# gpu-run finished:`; wait for that line, not for a process.
- GPU tests live in the packages' own test folders and run whenever CUDA is functional; `PM_TEST_GPU=1` requires them (the suite fails without a GPU), `PM_TEST_GPU=0` turns them off, and a suite that skips them says so in one line (`lib/ParticleMeshCore/test/gpu_switch.jl`).
- Work there in a worktree of your own under `.claude/worktrees/` (ignored by git), on your thread's branch or detached at its commit, never in the main checkout, which other sessions share. Remove only a worktree you made yourself, by its path, and tell the owner about any you leave behind. `git worktree prune`, `git worktree repair` and `git gc` stay denied in `.claude/settings.json`.

## Issues

- Open and comment on issues in this repository freely, one problem per issue. Search the open issues first and comment on a match instead of opening a duplicate. Label it for routing: `upstream` (a suspected bug in a dependency or in Julia), `factory` (the setup or the process: denied actions, depots, the GPU queue, tooling, a rule in this file that cannot be followed, goals that contradict each other; say what you tried, the exact error, the workaround, the time lost), `bug` (a defect in this repository outside your task), `follow-up` (work you found and left). Then continue.
- Never post in another repository, and never edit, delete or transfer an issue. Close an issue only through a merged PR whose description says `Fixes #<n>`; humans and sessions outside the factory close the rest. Issues are public: the rules for this repository's content apply to them, and the CI scan does not see them.
- A suspected upstream bug goes to a fresh `upstream-reporter` subagent (`.claude/agents/upstream-reporter.md`): it reduces the problem to a minimal working example that does not depend on this repository, confirms it in a clean temporary environment and posts it as an `upstream` issue here. Meanwhile work around it, except for Reactant failures, which are parked instead (A9). Humans and sessions outside the factory file it upstream.
- Never retry a denied action another way; open a `factory` issue.

## Background jobs and waiting

- Never wait for another process with a loop over `pgrep -f "<pattern>"`: the waiting shell's own command line contains the pattern, so the loop waits on itself (this has stalled a queued benchmark for twenty minutes before). Chain dependent work in one command (`cmd1; cmd2`, or `&` and `wait`), or wait on the exact PID (`while kill -0 <pid> 2>/dev/null; do sleep 10; done`). To wait for a condition, such as a line in a log file, use the Monitor tool; a session under exact allow lists (see "Working here") can wait no other way. If a pattern is unavoidable, write it so it cannot match itself: `pgrep -f '[b]ench.jl'`.
- In a cloud session a job started with `nohup` or `&` dies between turns: start it as a background task of the session. Julia buffers its output into a file in blocks, so an empty log is not a hang.

## Julia notes

- Find a package's location with `julia +1.13 --startup=no --project -e "using X; Base.pkgdir(X)"`; package versions are in the `Manifest.toml` of the environment you are in (a manifest may be versioned per Julia release, `Manifest-v1.13.toml`).
- Test and docs environments use `[sources]` to reach the packages in this repository; do not `Pkg.develop` over them.
- Use a library through its own interface, as its authors intend (its options, traits, callbacks and AD backends), and keep our layer over it thin: an idiomatic use shows design problems in the package underneath, and a wrapper hides them. When the idiomatic route costs something, measure it and file the issue instead of coding around it.
- Enzyme's CUDA rules load with CUDA itself, not with CUDACore alone: an environment that differentiates on the GPU has `using CUDA` next to CUDACore.
- The jld daemon (the julia-daemon skill, installed outside this repository) saves load and compile time where it runs. Where `jld` is installed, try `jld start` once; if it fails, use plain `julia +1.13` runs for the rest of the session and put several checks into one process rather than one run per check.
- Prefer `foreachindex`-style KernelAbstractions kernels; `Atomix` for atomics; `Adapt` for structs crossing to the device.
